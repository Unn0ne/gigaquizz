Gigaquizz — сервис минутных опросов на Go с анонимным голосованием и защищённым кабинетом организатора.

[Архив полного диалога о проекте](docs/dialogue/README.md) содержит сообщения пользователя, ответы и промежуточные обновления ассистента с начала обсуждения, в Markdown и JSON.

[Пошаговый запуск сайта и стендов](docs/launch.md) · [Серверы и расчёт production](docs/production.md). Для production подготовлена воспроизводимая модель одного региона и трёх зон: число Go-узлов зависит от измеренной мощности полного HTTP-пути, Kafka рассчитывается отдельно по входу, репликам, сети и хранению. Условный кандидат сметы — 39 узлов плюс CDN/LB; это не подтверждённый минимум и не готовый установщик массового production.

Следующий шаг после RAM — [пакетный формат Kafka](docs/frame-benchmark.md): `Store.SubmitFrame`, общий заголовок 80 B и 28 B на попытку, квитанция с индексом внутри frame, потоковый replay и отдельный `cmd/framebench`. Положительный ответ выдаётся после commit Kafka. Старый формат совместим; новый путь пока не включён в интерфейс основного сайта.

[Измерения компактного журнала](docs/frame-results.md): на плане 200 тыс./с подтверждены все 12 млн попыток; на плане 1,7 млн/с — 70,25 млн из 102 млн (1,17 млн/с), с отказами заполненных очередей и пропусками генератора. После закрытия опросов выполнен принудительный перезапуск всех трёх локальных брокеров, без перезапуска ОС; заново сверены все 82 323 942 подтверждения новой серии, расхождений нет. Полностью сохранённый поток 1,7 млн/с и production HTTP этим ещё не подтверждены.

По запросу о 1,7 млн/с выполнен отдельный [эксперимент с CPU-ядром](docs/core-results.md): два минутных прогона приняли по **108 млн уникальных голосов (1,8 млн/с)**; второй обработал ещё 5,4 млн дублей, всего **1,89 млн попыток/с**. В обоих нет пропусков и отказов, каждый принятый ID и выбор проверен после закрытия. Пик RSS около 2,74 GiB. Это точное состояние в RAM одного Go-процесса, без HTTP, Kafka, диска и сохранности при падении; результат не повышает подтверждённую производительность надёжного журнала. [Устройство и команды](docs/core-benchmark.md).

Для целевых 100 млн голосов/мин подготовлен [пересмотр массового приёма: пакетный журнал и последующая дедупликация](docs/architecture-revision.md). По запросу пользователя реализован и испытан изолированный прототип `internal/votelog` + `cmd/logbench`: Go принимает попытки, Kafka сохраняет транзакционные пакеты, затем точный пересчёт формирует результат и manifest. Экспериментальный HTTP возвращает `202` за сохранённую попытку. Основной Go/PostgreSQL-сервис ниже сохраняет свой API с окончательной квитанцией.

[Результаты испытаний журнала](docs/log-results.md) включают успешные и неудачные нагрузки, отдельные HTTP/direct-профили и управляемые отказы. Устойчивая работа при отказе и целевые 100 млн/мин пока не подтверждены; прямой вызов хранилища не измеряет производительность HTTP. [Команды и границы эксперимента](docs/log-benchmark.md), [локальный Kafka-стенд](docs/kafka-lab.md). Публикация результатов журнала в административную БД и распределённое назначение владельцев ещё не реализованы.

[Предыдущая серия старого формата до 200 000/с](docs/log-expansion-results.md): четыре минутных прогона и CPU-профиль HTTP. Лучший direct-прогон подтвердил 9,42 млн попыток за минуту, HTTP при заданных 200k/с — 3,74 млн. Полностью обслуженный поток 200k/с в той серии не подтверждён. Повторная точная сверка всех 23 262 334 новых квитанций прошла без расхождений; пропуски генератора и отказы по времени сохранены в отчёте.

Рабочий вертикальный срез: создание A/B, single choice и multiple choice → ссылка для участников → голосование ровно в течение 60 секунд → промежуточные и окончательные обезличенные результаты. Один браузерный ID на опрос, первый принятый выбор окончательный. Одновременно может идти один опрос; пересекающиеся расписания отклоняются. Список показывает 100 последних по времени начала опросов.

Это реализация корректного приёма и восстановления для разработки. Производительность 100 млн голосов за минуту и отказоустойчивость при потере зоны/региона ещё не подтверждены. Локальная PostgreSQL не является кластером высокой доступности. Расчётная база остаётся 1 666 667 уникальных голосов/с; конверсия повторно не применяется. См. [подробную архитектуру и расчёты](docs/architecture.md), [историю архитектурных решений](architecture-notes.md), [ADR](docs/decisions.md), [API](docs/api.md), [эксплуатацию](docs/runbook.md), [нагрузочные испытания](docs/load-testing.md), [фактически выполненные проверки](docs/verification.md).

Быстрый локальный запуск из корня проекта:

```sh
make dev
```

Для отдельного стенда с primary и двумя физическими репликами:

```sh
make lab-up
make replication-test
make lab-status
```

Отказный тест управляет только узлами `.local/replication-lab`: останавливает реплики, отменяет SyncRep, проверяет квитанции, продвигает реплику и восстанавливает старый узел из новой копии. Его нельзя запускать одновременно с нагрузочным прогоном на том же стенде. Обычный dev-кластер и `.env` не меняются. Инструкции: [стенд](docs/replication-lab.md), [проверка сохранности](docs/replication-durability.md), [генератор нагрузки на хранилище](docs/storage-benchmark.md), [результаты измерений и отказных испытаний](docs/replication-results.md).

На локальном стенде проверены шесть профилей: после переключения primary сохранились все 123 088 подтверждённых тестовых голосов. Профиль 3000 новых голосов/с с 20% конфликтующих повторов выполнен в течение 10 секунд без пропусков; при заданных 6000/с генератор пропустил 3,19% ключей. Эти измерения относятся к хранилищу на одном компьютере, без HTTP, и не определяют устойчивую производительность серверной группы.

Следующая серия включает 55-секундные прогоны настоящего HTTP API, прогрев пулов, фазовые метрики и сокращение начального ожидания WAL. При 4000/с подтверждены все 220 000 голосов, p99 ≤21 мс. При 6000/с есть прогоны без пропусков и неудачные повторы; устойчивая мощность не подтверждена. Все результаты и воспроизведение — в [отчёте о настройке нагрузки](docs/load-tuning.md).

Режим реплицированного подтверждения включается через `DURABILITY_REQUIRED_STANDBYS` и `DURABILITY_STANDBY_NAMES`; пример для стенда — `1` и `gigaquizz_ha_a,gigaquizz_ha_b`. Он проверяет WAL на фиксированном primary и именованных физических репликах, включая повторные квитанции и чтение итогов. Нулевое/пустое значение оставляет локальную БД; непустая серверная настройка синхронной репликации без явной политики клиента не принимается. Это механизм для испытаний с контролируемым владельцем, без автоматического failover и гарантии независимых зон.

Нужны Go 1.26.1+, Python 3 и PostgreSQL 16+ либо запущенный Docker. Скрипт использует установленный PostgreSQL/Postgres.app, если доступен; иначе запускает PostgreSQL 18 через Compose. Создаёт отдельное хранилище в `.local/postgres` либо Docker volume и `.env` с случайным паролем. Существующие `.env` и данные сохраняются. Для Postgres.app используется Unix socket в `.local`, TCP у локальной БД выключен; доступ к каталогу ограничен владельцем. Пароль администратора находится в `ADMIN_PASSWORD` файла `.env`, в консоль не выводится.

Откройте адрес из `PUBLIC_URL` в `.env` и перейдите в `/admin`. По умолчанию адрес — `http://127.0.0.1:8080`. Если порт занят, измените обе строки `HTTP_ADDR` и `PUBLIC_URL` на один свободный порт, например `127.0.0.1:8088` / `http://127.0.0.1:8088`. Пользуйтесь тем же origin, что указан в `PUBLIC_URL`: он проверяется для запросов из браузера.

В кабинете создайте вопрос, укажите варианты и выберите начало сейчас либо заранее. Скопируйте ссылку для участников. Свободный текст ответов отсутствует; для вопроса допустимы 1–300 символов, 2–20 вариантов по 1–100 символов. A/B требует два варианта. Это текущие ограничения вертикального среза, расширяемые отдельным изменением контракта. Результаты обновляются кнопкой, без постоянного polling от участников.

Для собственной PostgreSQL скопируйте `.env.example` в `.env`, задайте URL и уникальный случайный пароль администратора, затем:

```sh
make run
```

Миграция применяется при запуске транзакционно, с блокировкой от конкурентного применения. Отдельная команда для выпуска миграций:

```sh
go run ./cmd/gigaquizz -migrate-only
```

Переменные процесса имеют приоритет над `.env`. `.env` читается как данные, без исполнения shell. В нём нельзя оставлять шаблонный пароль из примера. Настройки: `HTTP_ADDR`, `PUBLIC_URL`, `DATABASE_URL`, `ADMIN_PASSWORD`, `VOTE_DB_CONNECTIONS` (64), `MAX_INFLIGHT` (256). Админка использует отдельный пул из 8 соединений; публичные чтения ограничены 16 обработчиками, голосования — `MAX_INFLIGHT`. Эти значения — ограниченные стартовые настройки, не результат измерений пропускной способности.

Перед открытием HTTP-listener приложение заранее устанавливает все соединения обоих пулов. При недоступности нужной БД/репликации запуск завершается ошибкой в пределах startup timeout 30 секунд. Соединения следует готовить заранее, до начала минутного события.

Сборка и проверки:

```sh
make build
make check
```

`make check` выполняет vet и Go-тесты с race detector. Реальные тесты БД включаются через `TEST_DATABASE_URL`: они создают отдельные случайные схемы и удаляют только свои схемы, не меняя таблицы приложения. Пример для локального Unix socket:

```sh
TEST_DATABASE_URL="postgres://gigaquizz@/gigaquizz?host=$PWD/.local&port=55432&sslmode=disable" make integration
```

Для браузерного теста на запущенном локальном сервисе:

```sh
npm ci
npx playwright install chromium
E2E_BASE_URL=http://127.0.0.1:8080 npm run test:e2e
```

На macOS тест использует установленный Google Chrome, если он есть; установка Chromium тогда не нужна. `E2E_BASE_URL` должен совпадать с `PUBLIC_URL`, пароль читается из `ADMIN_PASSWORD` окружения или `.env`. Тест создаёт реальный минутный опрос: выполняйте на локальной/тестовой БД без другого активного опроса. Он проверяет создание через интерфейс, вкладки, повторное открытие, потерю подтверждения после записи, настоящий дедлайн, итоговые числа и выход администратора. Скриншоты остаются в игнорируемом `.local/screenshots`; трассировки с телами запросов выключены.

Для вызовов API без помещения пароля в shell history можно использовать стандартный Python:

```python
import http.cookiejar, json, urllib.request
from pathlib import Path

env = dict(line.split('=', 1) for line in Path('.env').read_text().splitlines()
           if line and not line.startswith('#'))
base = env['PUBLIC_URL']
client = urllib.request.build_opener(urllib.request.ProxyHandler({}),
    urllib.request.HTTPCookieProcessor(http.cookiejar.CookieJar()))
def post(path, body):
    request = urllib.request.Request(base + path, json.dumps(body).encode(),
                                     {'Content-Type': 'application/json'})
    return json.load(client.open(request))
post('/api/admin/login', {'password': env['ADMIN_PASSWORD']})
poll = post('/api/admin/polls', {
    'question': 'Какой вариант выбираем?', 'type': 'single', 'options': ['A', 'B']})
print(poll['id'])
```

Небольшой нагрузочный прогон для созданного опроса:

```sh
go run ./cmd/loadtest -url http://127.0.0.1:8080 -poll POLL_UUID -rate 10 -duration 10s -duplicate-every 5
```

Это 100 запланированных логических голосований с дополнительными повторами, а не подтверждение масштаба. Генератор отдельно считает HTTP-попытки, полученные подтверждения, неопределённые исходы и собственные пропуски расписания. Полномасштабный прогон требует отдельного плана и бюджета.

Остановка приложения — Ctrl+C: оно прекращает приём, ждёт обработчики и останавливает фоновую финализацию перед закрытием пулов. Локальная БД остаётся для следующего запуска. Docker можно остановить `docker compose stop db`; локальный кластер — `pg_ctl -D .local/postgres stop -m fast` из подходящего каталога PostgreSQL bin. Команды удаления данных не включены в обычный запуск/остановку.

Структура:

| Путь | Ответственность |
|---|---|
| `cmd/gigaquizz` | Конфигурация, HTTP, фоновые задачи, завершение |
| `internal/poll` | Типы вопроса, доменные ограничения, интерфейс хранилища |
| `internal/httpapi` | API, административные сессии, HTTP-границы и лимиты |
| `internal/postgres` | Схема, атомарная запись, дедлайн и финальные результаты |
| `internal/votelog` | Изолированный прототип Kafka: допуск, транзакционные пакеты, fencing, CLOSED, точная сверка и экспериментальный HTTP |
| `internal/web` | Встроенные HTML/CSS/JS, без сборки фронтенда и внешних сервисов |
| `cmd/loadtest` | Ограниченный генератор с открытым расписанием |
| `cmd/storagebench` | Нагрузка на хранилище, измерения WAL и сверка каждого ключа после закрытия/восстановления |
| `cmd/logbench` | Минутные HTTP/direct-профили журнала, приватный ledger квитанций, пересчёт и явное восстановление |
| `internal/votecore` | Экспериментальное точное ядро в RAM: полный ID, первый выбор, серверный дедлайн и финализация |
| `cmd/corebench` | Потоковый генератор до 180 млн попыток и полная сверка RAM до завершения процесса |
| `scripts/profile_core.py` | Ограниченный CPU-профиль с телеметрией процесса, без сети и диска в пути приёма |
| `cmd/framebench` | Минутный direct-профиль компактных Kafka frames и повторная потоковая сверка по приватному manifest |
| `scripts/production_capacity.py` | Модель серверов при потере одной зоны: явные допущения и чувствительность к измеренной мощности |
| `scripts/replication_lab.py` | Изолированные primary и два standby, управляемые отказы и rebuild |
| `scripts/kafka_lab.py` | Три локальных Kafka-брокера с проверкой принадлежности стенду и управляемыми отказами |
| `scripts/profile_log.py` | Воспроизводимые профили журнала, агрегатная телеметрия и расписание отказных действий |
| `tests/browser` | Проверка полного пользовательского пути |

Зависимости зафиксированы в `go.mod`, `go.sum` и `package-lock.json`. PostgreSQL 16.3 из доступного Postgres.app использован для локальной интеграционной проверки; для развёртывания выбирается поддерживаемая актуальная версия с обновлениями безопасности. pgx и Playwright используются как драйвер и тестовая зависимость соответственно. Их наличие не задаёт готовность к расчётному масштабу.
