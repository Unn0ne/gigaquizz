# Запуск файлового стенда

Стенд измеряет один Go-процесс: генератор → ограниченная очередь → бинарный файл → синхронизация на диск → подтверждение. PostgreSQL и Kafka ему не нужны. Это отдельный пакетный эксперимент; сайт в этой ветке также использует файлы, но принимает отдельные HTTP-запросы и имеет другой профиль затрат. [Результаты испытаний](file-results.md), [архитектура и ограничения](simplification.md).

Нужны Go из `go.mod`, Python 3.11+, macOS или Linux и локальный диск. На macOS writer использует `F_FULLFSYNC`, на Linux — `fsync`. Неподдерживаемая синхронизация завершает работу ошибкой. Один файл принадлежит одному writer; режим совместной записи по сети не реализован. Контракты синхронизации: [Apple](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fcntl.2.html), [Linux](https://man7.org/linux/man-pages/man2/fsync.2.html).

```sh
go build -o bin/filebench ./cmd/filebench
make file-test

# Каждый прогон длится полную минуту; старт через 15 секунд подготовки.
GOMEMLIMIT=6GiB python3 scripts/profile_file.py --label files_smoke -- -rate 1000 -repeat-every 5 -allow-large
GOMEMLIMIT=6GiB python3 scripts/profile_file.py --label files_200k -- -rate 200000 -allow-large
GOMEMLIMIT=6GiB python3 scripts/profile_file.py --label files_1700k -- -rate 1700000 -allow-large
GOMEMLIMIT=6GiB python3 scripts/profile_file.py --label files_1700k_repeats_1pct -- -rate 1700000 -repeat-every 100 -allow-large
```

Метки должны быть новыми: прежние результаты не перезаписываются. Обёртка снимает CPU, RSS и свободное место раз в секунду, сохраняет SHA-256 бинарника и останавливает свой дочерний процесс при нарушении лимитов. Во время измерения не запускайте другие нагрузочные тесты или сборку.

По умолчанию: 64 работника, frame до 4096 попыток, группа синхронизации до 32768 попыток, ожидание заполнения до 10 ms, очередь Store до 262144 попыток. Размер группы меняется через `-batch-size`, очередь — через `-store-queue`, ожидание — через `-linger`. Ограничение группы — 131072, очереди — 1048576; повышение лимитов само по себе не доказывает нужную пропускную способность.

`-rate` задаёт **новые ID/с**; `-repeat-every 20` добавляет 5% попыток с прежним ID и другим выбором. Пределы стенда: 1,8 млн новых ID/с, 120 млн попыток за минуту, 4 GiB журнала на запуск, 8 GiB всех журналов и 1 GiB клиентских ledgers. До запуска резервируются расчётное место и ещё 8 GiB свободного диска. Старые журналы автоматически не удаляются.

Артефакты:

- `.local/file-profiles/<label>.json` — агрегаты, задержки, ошибки, точная сверка;
- `.local/file-profiles/<label>_telemetry.json` — среда, контрольная сумма, ресурсы;
- `.local/filebench/logs/filebench_*/` — неизменяемый `poll.json` и `votes.wal`;
- `.local/filebench/ledgers/` — приватный эталон генератора и полученные квитанции, исключены из Git.

Поле `private_manifest` отчёта указывает вход для повторной проверки **новым процессом**:

```sh
GOMEMLIMIT=6GiB bin/filebench -audit-only .local/filebench/ledgers/filebench_<run>.json
```

Сверка читает весь закрытый журнал, проверяет контрольные суммы и последовательность, восстанавливает каждый полный 128-битный ID, сравнивает выбор, время допуска и каждую подтверждённую frame-квитанцию. Для синтетических ID используется обратимая AES-перестановка; это точный проверочный алгоритм, а не готовый production-пересчёт произвольных браузерных ID.

Расписание генератора использует монотонные часы. Допуск Store и проверка времени квитанции используют календарное UTC-время из неизменяемого расписания опроса; разные типы часов нельзя смешивать при проверке границы.

Счётчики разделяют неотправленные попытки генератора, `Busy`, закрытие, неопределённый исход и отсутствующие подтверждённые записи. Нулевая потеря ACK не означает, что обслужен весь план: смотрите также `planned`, `recorded`, `skipped`, `busy` и остальные отказы.

`make file-test` включает реальные файлы, ошибки записи/синхронизации, дедлайн, порчу журнала и убийство дочернего writer через SIGKILL с независимым учётом ACK в родителе. Ни этот тест, ни повторная сверка не отключают питание, не теряют диск и не проверяют отказоустойчивость HTTP-сервиса. Успешный системный вызов синхронизации остаётся контрактом ОС и накопителя.
