# Локальные проверки 13 сентября 2026

[Разбор результатов и замечаний ревью](../../../review-scale.md). `summary.json` суммирует разные прогоны, включая прежние серверы и промежуточный кандидат. Это не одно событие на 100 млн участников.

В каждом `r13_*.json` есть конфигурация, SHA-256 бинарников, генератор, независимая сверка и результат после перезапуска. `correct=true` означает успешную проверку сохранённых данных. Если первоначальный прогон не закончил финализацию, он остаётся `correct=false`; отдельная последующая сверка после ручного восстановления находится в `recovery_report`. Приём всего запланированного потока проверяется отдельным `load_coverage` (либо отношением ACK/план для провалившегося прогона); пропуски, отказы и ошибки открытия не исключены из знаменателя. При нескольких генераторах их отдельные отчёты находятся в `generator_reports`, общие percentiles не выдумываются.

`workload_resource_samples` содержит отсчёты CPU и RSS без PID. Средний CPU вычисляется по разности CPU time за интервал наблюдений одного процесса; максимальный наблюдавшийся RSS не равен точному пику. Клиенты, приложение и все БД делят ноутбук. Байты HTTP-тела не включают заголовки и транспорт. WAL bytes — наблюдение файлов, не физическая гарантия сохранности при потере диска.

- `baseline-provenance.json` — исходные коммиты и замороженные бинарники до изменений.
- `candidate-provenance.json` — промежуточная версия до последнего исправления закрытия группы, точности receipt и повторного использования gzip-декодера.
- `candidate2-provenance.json` — код большинства новых нагрузочных профилей до обнаружения зависания финализации Kafka. Бинарники собраны с изменениями поверх `base_commit`; VCS metadata бинарника не указывает на последующий коммит публикации. Фактический код определяется SHA-256 каждого исходного файла.
- `candidate3-provenance.json` — заключительное исправление автоматической финализации после terminal writer failure и фиксированные категории ошибок. В files изменён только общий список разрешённых метрик; алгоритм записи остался как в candidate2.
- `checks.json`, `*-service.json`, `*-browser.json`, `postgres-kafka-real-regressions.json` — функциональные проверки и их границы. Часть последних результатов сохранена как сводка stdout инструментального запуска, что явно отмечено.

Полные планы, seed, ID участников, клиентские журналы, пароли и конфигурации опросов остаются в игнорируемой `.local`.

Для повторения соберите бинарники нужной ветки перед нагрузкой. Пример верхней ступени files:

```sh
make build
python3 scripts/profile_full_http.py \
  --mode simple-files --label files_100k_p1_g2_w2048 \
  --rate 100000 --workers 2048 --generators 2 \
  --max-inflight 8192 --file-partitions 1 --port 8093
```

Для Kafka нужны заранее запущенные локальные PostgreSQL и три принадлежащих проекту брокера, а также `TEST_DATABASE_URL` в приватном окружении:

```sh
make build
python3 scripts/profile_full_http.py \
  --mode postgres-kafka --label kafka_50k_p16_g2_w4096 \
  --rate 50000 --workers 4096 --generators 2 \
  --max-inflight 16384 --partitions 16 --batch-votes 1024 --port 8094
```

`--journey --definition` включает пять GET с gzip перед первым POST каждого ID. `--max-lag-ms` задаёт клиентский бюджет опоздания; в основных профилях 100 ms, в отдельно подписанном диагностическом — 1000 ms. Окно сервера всегда остаётся 60 секунд. [Полная процедура, ограничения и ручная сверка](../../../http-benchmark.md).
