Эксперимент с ядром Go без сети и диска

`internal/votecore` и `cmd/corebench` проверяют вычислительную часть минутного голосования. Это отдельный эксперимент: успешный `Accepted` означает запись в RAM текущего процесса. Завершение процесса теряет все голоса. HTTP, Kafka, fsync, репликация, отказоустойчивое подтверждение и административная публикация в этот путь не входят. Основной сервис и прототип журнала продолжают использовать свои прежние реализации и гарантии.

Цель этого этапа — измерить реальную обработку порядка 102 млн уникальных ID за 60 секунд, включая проверку выбора, серверного дедлайна, точную дедупликацию и подсчёт. Результаты измерений находятся в [core-results.md](core-results.md). Этот тест не заменяет [испытания журнала](log-expansion-results.md).

Устройство ядра

- Один заранее подготовленный опрос, окно ровно 60 секунд. `SHA-256(poll_id || token)` распределяет полные 128-битные ID между 256 или 512 частями одного процесса. Это части состояния в RAM, а не отдельные кластеры или машины.
- Каждая часть содержит mutex, точную `map[[16]byte]uint32` и 32 счётчика вариантов. Хеш выбирает часть, но совпадение полного ID определяет дубль. Первый допущенный выбор окончательный; повтор возвращает прежний выбор.
- Проверка времени выполняется внутри блокировки непосредственно перед допуском. После дедлайна новые и повторные отправки получают `Closed`. Уже допущенная запись может закончиться после дедлайна. `Seal` необратимо закрывает приём и ждёт завершения допущенных критических секций.
- Лимит записей разделён между частями. Переполнение одной части даёт `CapacityExceeded`, даже если в других осталось место. Для случайных ID генератор готовит `max(ceil(N × 1,05), shards × 1024)` мест. Это запас для данного распределения, не гарантия при произвольном перекосе.
- В горячем пути нет отдельной горутины, канала, контекста или глобального счётчика на голос. Состояние результата и дедупликации изменяется под одной блокировкой. Предварительное выделение памяти входит в подготовку до начала опроса.

Расписание и проверка результатов

Генератор создаёт уникальные 128-битные ID как AES-перестановку разных значений счётчика. Случайный ключ AES сохраняется только в приватном тестовом manifest. На каждого worker приходится небольшой повторно используемый буфер, а не весь набор запросов. Один процесс выполняет и генерацию, и ядро, поэтому стоимость генерации включена в измерение.

У каждого нового ID есть исходный момент отправки на равномерном расписании. Буфер обрабатывается группами: worker ждёт момента последнего элемента группы и повторно проверяет время после пробуждения. Раньше своего расписания ни один элемент не отправляется. Задержка объединения ограничена параметром `-coalesce` и размером буфера. Попытки с отставанием более `-max-lag` явно считаются пропущенными генератором; их нельзя вычитать из знаменателя успешности. Поток не замедляет собственное расписание вслед за ответами ядра.

`-repeat-every 20` добавляет ещё одну попытку для каждого двадцатого ID сразу после первой, с конфликтующим выбором 2 вместо 1. Это увеличивает количество попыток на 5%, сохраняя количество запланированных уникальных ID. Нагрузочные повторы здесь последовательные; конкурентные конфликтующие повторы отдельно покрыты race-тестом ядра.

Каждый принятый выбор фиксируется в независимом bitmap: два бита на логический ключ. Worker владеет целым буфером, кратным четырём ключам, поэтому workers не записывают в один байт одновременно. Для 102 млн ключей bitmap занимает 25 500 000 байт. После `Seal` генератор заново создаёт каждый принятый полный ID и через `Lookup` проверяет наличие и исходный выбор. Проверка числа записей и всех 32 счётчиков дополнительно обнаруживает лишние записи. Это полная сверка принятых ключей, без выборки или вероятностной дедупликации.

Latency измеряется для ключей, у которых младшие 10 бит AES-ID равны нулю: ожидаемая выборка 1/1024, независимая от worker, позиции в буфере и успешности ответа. Малые прогоны до 10 000 попыток измеряют каждую отправленную попытку. Гистограмма сохраняет верхнюю границу интервала; погрешность округления менее 6,25% начиная с 32 ns. Поля p95/p99 относятся к выборке, а не ко всей совокупности. Отдельно показано время от исходного расписания и от вызова `Submit`; пропуски генератора latency не имеют.

Для успешной проверки нужны одновременно пустой `errors`, нулевые счётчики неверного выбора / повторного принятия и `reconciliation.correct=true`. Одного совпадения агрегатов недостаточно. Число пропусков или отказов при этом может быть ненулевым: доля обслуженных попыток и сохранность принятого RAM-состояния оцениваются отдельно.

Воспроизведение

```sh
go build -o bin/corebench ./cmd/corebench
go test -race -count=1 ./internal/votecore ./cmd/corebench

# Контроль: реальная минута, 60 000 новых ID + 12 000 повторов.
python3 scripts/profile_core.py --label smoke_1000_repeat5 -- \
  -rate 1000 -workers 8 -shards 256 -repeat-every 5 -allow-large

# 102 млн новых ID за минуту, без дополнительных повторов.
python3 scripts/profile_core.py --label target_1700k -- \
  -rate 1700000 -workers 8 -shards 256 -buffer-size 256 \
  -coalesce 250us -max-lag 20ms -allow-large

# Повтор успешного профиля: 108 млн новых ID + 5,4 млн конфликтующих дублей.
python3 scripts/profile_core.py --label headroom_1800k_repeat20 -- \
  -rate 1800000 -workers 8 -shards 256 -buffer-size 256 \
  -coalesce 250us -max-lag 100ms -repeat-every 20 -allow-large
```

Каждый label должен быть новым: старые отчёты не перезаписываются. Перед измерением остановите другие нагрузочные задания; состояние фоновых сервисов зафиксируйте в описании результатов. `profile_core.py` ставит блокировку против одновременных core/log-профилей, ограничивает процесс 300 секундами, сохраняет раз в секунду CPU time и RSS, команду, SHA-256 бинарника, версию Go, параметры GC, память и swap до/после. В дочернем процессе явно задан `GOMEMLIMIT=10GiB`; это настройка Go, а не системный жёсткий лимит RSS. Принудительное завершение считается незавершённым тестом, а не успешной сверкой.

Границы генератора: от 1 до 3 000 000 новых ID/с, максимум 180 млн попыток с учётом повторов, 1–16 workers, буфер 4–1024 элемента кратно четырём, задержка объединения 100µs–1ms, допустимое отставание до 100ms. Большая нагрузка требует `-allow-large`. Длительность всегда 60 секунд; перед ней предусмотрено 10 секунд на подготовку. Если выделение памяти не успело, тест завершается до нагрузки. Расписание генерации использует монотонные часы, а допуск и ожидание `Seal` — календарное время сервера; раннее пробуждение или коррекция часов не дают права закрыть ядро до его дедлайна.

Агрегатные отчёты и телеметрия находятся в `.local/core-profiles`. Manifest с тестовыми ID-параметрами и bitmap имеют права 0600 в `.local/corebench`, ограничены 64 файлами / 512 MiB. Harness сохраняет резерв свободного диска 8 GiB. Приватные файлы позволяют восстановить набор ожидаемых синтетических ключей, но не состояние уже завершённого ядра. Поэтому сверка проводится при жизни процесса; проверки сохранности после его падения у этого режима нет.
