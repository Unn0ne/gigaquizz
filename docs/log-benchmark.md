Испытания прототипа журнала Gigaquizz.

`cmd/logbench` выполняет изолированный эксперимент новой архитектуры: Go admission → Kafka transactional batch → подтверждение попытки → чтение `read_committed` → точная дедупликация → итог и manifest в JSON. Основной PostgreSQL-сервис и его публичный API этот инструмент не заменяет. Публикация новых результатов в административную БД, распределённое назначение владельцев и публичное восстановление квитанций через UI ещё не реализованы. [Архитектура и компромиссы](architecture-revision.md), [описание трёх локальных брокеров](kafka-lab.md).

Сборка и проверки из корня репозитория:

```sh
make build
make kafka-up
make kafka-test
```

Интеграционные тесты создают небольшие синтетические темы с собственным префиксом и сохраняют их для проверки. Они используют только управляемый стенд из `.local/kafka-lab`; сторонние адреса не принимаются. Брокеры и генератор работают на одном компьютере. Не запускайте Go-тесты, несколько нагрузок или административные Java CLI во время обычного измерения: они конкурируют за те же ресурсы. Отказные профили намеренно выполняют остановку/возврат брокера, и эта дополнительная работа входит в их условия.

Пример настоящего минутного HTTP-профиля:

```sh
python3 scripts/profile_log.py --label http_6000_example -- -mode http -rate 6000 -duration 60s -workers 512 -queue 8192 -partitions 8 -batch-size 1000 -linger 20ms -allow-large
```

Каждая команда создаёт новый опрос и topic RF3/minISR2, прогревает writers и HTTP перед заранее заданным стартом, запускает расписание, дожидается закрытия и сверяет результаты. Имена профилей не переиспользуются. `-duration` задаёт только окно новых попыток; сам опрос всегда длится 60 секунд. При 60s нагрузка продолжается до самого закрытия без прежнего пятисекундного запаса. Запрос, запланированный до дедлайна, может быть доставлен поздно и получить `closed`; исключать его из числа запланированных нельзя.

| Флаг | Значение и ограничение |
|---|---|
| `-mode http` | Настоящий экспериментальный HTTP handler через loopback; генератор и сервис в одном Go-процессе |
| `-mode direct` | Прямой `Store.Submit`; исключает HTTP, но сохраняет очереди, проверку времени и commit Kafka |
| `-rate` | Новые уникальные ключи/с, максимум 200 000; дополнительные повторы считаются сверх этого потока |
| `-duration` | До 60s; опрос всегда 60s |
| `-repeat-every 5 -different-choice` | Дополнительная конкурентная попытка с другим выбором для каждого пятого ключа |
| `-workers` | Одновременно ожидающие попытки, максимум 8192; ограничение генератора, не количество Kafka writers |
| `-queue` / `-max-lag` | Ограниченная очередь генератора до 100 000 и опоздание до 10s; по умолчанию 1s |
| `-transaction-timeout` | Бюджет транзакции пакета 1–30s, по умолчанию 10s; положительный ответ по-прежнему требует commit |
| `-partitions` | До 64 для этого генератора; одному разделу соответствует один логический writer |
| `-batch-size` / `-linger` | До 4096 записей на транзакцию; ожидание 1–100ms |
| `-partition-queue` | До 8192 ожидающих записей на раздел, помимо активного пакета |
| `-allow-large` | Явный режим для >1000 попыток/с или >10 000 попыток; верхние пределы остаются |

Общий предел — 12 млн попыток, включая повторы. Нельзя одновременно запросить 200 000 новых ключей/с на 60s и ещё 20% повторов: это превысит предел. Приватный бинарный ledger ограничен примерно 864 MB на максимальный прогон, суммарно до 64 файлов/5 GiB. Полный аудит держит точные карты записей и ключей в памяти; их реальная память больше размера ledger, поэтому профиль максимального размера требует нескольких GB свободной RAM. Перед записью проверяется свободный диск; ранее сохранённые квитанции автоматически не удаляются. Контроллер Kafka также ограничивает использование диска стендом. Первоначальная серия использовала пределы 100 000/с и 6 млн; они расширены для следующей серии по запросу пользователя, без изменения кворума или минутного окна. После проверки фактического свободного места суммарный предел ledgers увеличен с 4 до 5 GiB для дополнительного сравнения linger; прежние файлы сохранены, минимальный свободный диск стенда 8 GiB не уменьшался.

Пакет записывается с `acks=all`, идемпотентностью и явным commit транзакции. Значение события — 80 B, Kafka key для голоса — ещё 16 B; framing, batch и transaction markers добавляются отдельно. Сжатие явно выключено. `202` приходит после успешного commit пакета и означает сохранённую попытку. Точный первый выбор определяется по минимальному committed offset в одном разделе. Он может отличаться от первого запроса по расписанию генератора, если два конкурентных запроса поменялись местами при доставке; это не смена уже принятого выбора.

Квитанция содержит partition, offset и серверное время допуска. В приватном ledger сохраняются также полный синтетический token, выбор и исход каждой попытки; файл имеет права 0600 и SHA-256 для проверки целостности. Обычный JSON-отчёт не содержит список токенов. Ключи теста состоят из случайного префикса и номера; распределение выполняется через SHA-256 от poll ID и полного token. Это воспроизводимая синтетическая нагрузка, а не браузерные идентификаторы реальных людей.

Отчёт разделяет:

- план уникальных ключей, план всех попыток и реальные отправки;
- пропуски генератора, `not_open`, `closed`, переполнение admission, неизвестные исходы и `202`;
- подтверждённые попытки, уникальные подтверждённые ключи и окончательные уникальные голоса;
- задержку от исходного расписания и от отправки, отдельно для всех отправок и для `202`;
- подтверждения, полученные после закрытия для ранее допущенных записей; это время получения ответа, не точное время commit внутри брокера.

p95/p99 вычисляются по отдельным наблюдениям без гистограммной аппроксимации. Пропуски остаются в знаменателе плана, но не имеют latency и не входят в выборку задержек. Расписание при кратком отставании может догоняться в пределах `max-lag`; секундные корзины показывают эту неравномерность. Очередь генератора не является надёжным приёмным журналом. `Store.Metrics` считает транзакции, размер пакетов и суммарное время их выполнения; сумма длительностей параллельных writers не является CPU time.

`profile_log.py` записывает отдельные snapshots `ps` примерно раз в секунду: накопленный CPU и RSS только Go-процесса и трёх JVM, без строк запросов и токенов. Go-процесс объединяет генератор и сервис, разделить их CPU этой телеметрией нельзя. CLI управления брокером создаёт промежутки между samples в отказном профиле; время действий записывается отдельно. Эти snapshots не являются профилем CPU/mutex/GC и не доказывают единственную причину ограничения.

Для диагностического прогона добавьте `--cpu-profile` перед разделителем `--`. Он создаст новый приватный `.local/kafka-lab/profiles/<label>.cpu.pprof` с CPU-профилем общего Go-процесса. Измеряемый период включает ожидание начала, нагрузку, дренирование и вычисление latency, но исключает последующее чтение Kafka и сверку. Такой прогон отмечается отдельно из-за накладных расходов профилирования. Обычные прогоны дополнительно сохраняют разности счётчиков выделений памяти и GC в `workload_diagnostics`; GC pause — только stop-the-world, а не всё время работы GC. Просмотр локального CPU-профиля:

```sh
go tool pprof -top bin/logbench .local/kafka-lab/profiles/ИМЯ.cpu.pprof
```

Ограничения процесса Go (`GOGC`, `GOMEMLIMIT`, `GOMAXPROCS`) и включение CPU-профиля записываются в telemetry. Автоматически менять их для улучшения числа RPS инструмент не будет.

Каждый `202` проверяется по конкретному partition/offset/token/choice/admission, затем независимый проход по записям определяет первый offset ключа и сравнивает канонический выбор и счётчики. После закрытия поздний POST отклоняется и для нового, и для прежнего token: он не записывает новую попытку. В этом прототипе восстановление прежнего исхода выполняет аудит; публичный endpoint канонической квитанции ещё не реализован. Совпадения одного общего количества недостаточно для успешной сверки.

Для серии до 200 000/с сверка дополнительно проверяет взаимно однозначную связь номера логического ключа с полным token и соответствие числа ключей заголовку ledger. Запись могут объяснять только отправленные попытки с `202` либо неизвестным исходом; окончательные отказы её не объясняют. Число записей каждого token/choice не может превышать число таких попыток. Это ловит ошибки генератора и лишние копии даже при совпадающем результате дедупликации. Дополнительная память ограничена bitmap ключей и счётчиками в уже существующей карте. Полный аудит по-прежнему выполняется в RAM; разрешение 12 млн попыток не означает возможность неограниченного увеличения нагрузки на том же компьютере.

Пример отказного профиля — SIGKILL одного брокера примерно через 40 секунд после запуска команды, затем его возвращение после 10 секунд ожидания. Точное смещение относительно начала опроса вычисляется по timestamps отчёта и fault events; 15 секунд подготовки входят во время до начала нагрузки.

```sh
python3 scripts/profile_log.py --label broker_failure_example --fault-node 1 --fault-after 40 --fault-duration 10 -- -mode http -rate 6000 -duration 60s -workers 4096 -queue 32768 -partitions 8 -linger 20ms -repeat-every 5 -different-choice -allow-large
```

Для отдельной проверки ожидания переключения можно явно задать `-transaction-timeout 30s -timeout 15s -max-lag 10s -workers 8192 -queue 65536`. Это увеличивает бюджет ожидания и накопления клиентских попыток; дедлайн серверного допуска не меняется. Прогоны с такими параметрами сравниваются отдельно: длинная очередь может скрыть задержку доставки, а её содержимое до admission/commit остаётся неподтверждённым. Поздние попытки после 60s всё равно отклоняются.

`--fault-node 1 2` проверяет потерю кворума, которая должна прекращать положительные подтверждения новых записей. Это отдельный сценарий за пределами устойчивого обслуживания при потере одной копии. Нагрузочный процесс остаётся жив, чтобы сохранить полученные квитанции. После завершения процесса повторная проверка использует путь ledger из JSON:

```sh
bin/logbench -audit-only .local/logbench/ИМЯ_ИЗ_ОТЧЕТА.ledger
bin/logbench -recover-and-seal .local/logbench/ИМЯ_ИЗ_ОТЧЕТА.ledger
```

Первая команда только читает. Вторая явно передаёт владение writers после остановки прежнего процесса, разрешает прежние транзакции, завершает CLOSED и выполняет ту же сверку. Проверяются исходный PID и эксклюзивная блокировка восстановления ledger. Одновременное восстановление владельца другим инструментом не координируется: production assignment/lease здесь отсутствует. Ошибка runtime-транзакции навсегда останавливает соответствующий writer до явного восстановления; он не пересоздаёт producer сам и не получает право вытеснять нового владельца.

При незавершённом первичном bootstrap, когда не во всех разделах есть committed BOOT, текущий прототип завершает восстановление по ограниченному timeout. До успешного bootstrap приём не начинается и подтверждённых голосов нет; перед событием готовится новый topic. Автоматическое восстановление такого частичного старта требует отдельного immutable manifest либо более полного протокола чтения разрешённого префикса. Уже успешный старт с последующим незавершённым пакетом восстанавливается и проверяется интеграционным тестом.

Ledger пишется после завершения попыток, перед Seal. SIGKILL самого процесса генератора во время нагрузки теряет ещё не сохранённые клиентские наблюдения и не позволяет провести такую же полную сверку; это не проверяется остановкой брокера. Результаты JSON и приватные ledgers сохраняются в `.local`; опубликованные агрегатные отчёты перечислены в итоговом отчёте испытаний. При переходе к независимым генераторам потребуется потоковая фиксация клиентских квитанций с отдельной моделью сохранности.
