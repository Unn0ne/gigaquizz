# Ревью и подготовка к большому опросу — 13 сентября 2026

Проверяются обе ветки: `simple-files` и `postgres-kafka`. Цель — один опрос, 100 млн участников за 60 секунд, первый сохранённый выбор одного браузера, подтверждение только после устойчивой записи. Скорость подсчёта менее важна, чем точность.

Это отчёт о коде и локальных проверках. Партиции внутри приложения и несколько генераторов нагрузки сами по себе не означают несколько серверов приложения. Тесты ядра из прежних отчётов также не подтверждают 1,67 млн HTTP-запросов в секунду.

Случайные 128-битные ID остаются ключами дедупликации браузера; срок их хранения не ограничен минутой. IP не используется. В открытые отчёты попадают только агрегаты; клиентские журналы, seed, пароли и конфигурации тестовых опросов остаются в `.local`.

## Что меняется при масштабировании

`FILE_PARTITIONS` задаёт 1–256 локальных журналов; существующие одиночные WAL продолжают читаться. Число партиций сохраняется в определении опроса и не меняется после старта. Все ответы одного ID попадают в одну партицию по SHA-256 от полного poll ID и token. Для Kafka поддерживается до 256 партиций и TLS/SASL для производственных подключений.

`MAX_PARTITION_UNIQUE_VOTERS` ограничивает таблицу одного пересчёта. При переполнении результат остаётся незавершённым с ошибкой; обрезанный результат не публикуется. По умолчанию предел равен общему, чтобы сохранялась возможность прочитать прежние большие одиночные журналы. Очередь и размер пакета задаются на партицию: при увеличении их числа нужно пересчитывать суммарную память и число writer. Для Kafka приложение заранее открывает все незавершённые опросы. Не нужно одновременно выставлять максимумы числа будущих опросов, разделов и очередей: 32 опроса по 256 разделов означают до 8192 writer/client. Горизонт предварительной подготовки пока не реализован.

На 100 млн ID и 128 партициях среднее — 781 250 ID на партицию. При условных 32 байтах на элемент это 25 MB одной таблицы вместо 3,2 GB для всего опроса. Это расчёт полезной таблицы: память Go map, GC, очередей и replay измеряется отдельно, а hash skew требует запаса. Общий финал публикуется только после CLOSED и точного результата каждой партиции.

| Отстающие или спешащие часы CDN преждевременно блокировали форму | Одна проверка времени сервера перед первым локальным отказом; тесты обеих ошибок часов |
| Глубокий пересчёт files удерживал общий mutex и мешал readiness | Перечитывание вынесено из общего замка; диагностика читает снимок списка опросов |
| Метрики исчезали после закрытия writer | Сохраняются реальные накопленные счётчики; исторические значения после рестарта не выдумываются |
| Генератор заново выделял gzip-декодер на каждый GET | Один повторно используемый декодер на последовательного worker; регрессия «повреждённый gzip → следующий исправный ответ» |
| Разные представления одного origin и низкий FD limit ломали общий план | Нормализация до записи плана, проверка диапазонов, файловых дескрипторов и суммарных ресурсов |
| Сигнал между запуском дочернего процесса и его регистрацией мог оставить процесс | Регистрация под маской сигналов, общее завершение собственных процессов; тесты прерывания при запуске |

Убраны неиспользуемые `Group.Config`, будущий `GroupConfig.OwnedPartitions` и `AppOptions.OwnedPartitions`: приложение пока не маршрутизирует разделы между узлами. Низкоуровневый Kafka Store поддерживает явное владение частью разделов и проверен отдельно. HTTP зависит от узких интерфейсов чтения и администрирования; диагностика публикует только разрешённые счётчики.

После этих исправлений выполнено ещё одно независимое чтение затронутого кода; новых замечаний в проверенных участках не осталось. Это не доказательство отсутствия всех ошибок.

## Функциональные проверки

- Обе ветки: сборка, `go vet`, полный набор Go-тестов с race detector. После последних изменений повторены затронутые пакеты. Python: 37 проверок files, 61 Kafka.
- Настоящий HTTP и SIGKILL в обеих ветках: 12 подтверждённых попыток → 3 уникальных голоса `[2,1]`; продолжение внутри минуты, восстановление после дедлайна, неизменный финал и поздний POST 410.
- Chrome: полный набор 15/15 в каждой ветке. После последнего исправления receipt — затронутые 12/12, включая два новых наносекундных случая. Полный итоговый набор из 17 тестов повторно не запускался. Проверены реальная минута, две потери ответа уже после ACK и независимое декодирование QR/PNG.
- Настоящие PostgreSQL/Kafka: потерянный ответ COMMIT создания, конкурирующие транзакции расписания, потеря сессии владельца, сохранённый и повреждённый финал. Два Store с разными разделами проверялись в одном OS-процессе; это не тест кластера приложений.
- Общий план нагрузки: проверена арифметика 100 млн ID в 17 диапазонах с 10% повторов, отсутствие пересечений, пропущенный генератор и точная сверка. Эта проверка плана сама не отправляет 100 млн HTTP-запросов.

## Нагрузочные измерения

Apple M1 Pro, 10 логических CPU, 32 GiB, Go 1.26.1; три Kafka-брокера и PostgreSQL тоже находятся на этом ноутбуке. Прогоны последовательные, окно каждого опроса — 60 секунд. Скорость в подписи — заданное число новых ID/s. `P` — разделы одного приложения, `workers` — конкурентность генератора. Это не число production-узлов. Подтверждения допущенных до конца запросов могут прийти после закрытия: отношение ACK/60 нормировано на окно допуска, а не на время получения всех ответов.

**ACK/план** показывает долю попыток с подтверждением. **Skip** — генератор не отправил попытку; **GET fail** — цепочка открытия не завершилась до POST; **Busy** — явный отказ при перегрузке; **Late** — отказ после дедлайна; **Early** — отказ до старта; **Unknown** — клиент не знает, сохранилась ли попытка. Эти категории нельзя прятать за нулём потерянных ACK.

Прежний сервер отдаёт исходные ресурсы без gzip и старый GET вопроса; новый — gzip и `/definition`. Обе версии в окончательных парах используют один и тот же новый генератор своей ветки. Для files на 5k это 512 workers, для Kafka — 2048: ветки между собой не получают одинаковую конкурентность. Обычно цепочка GET должна уложиться в 100 ms от запланированного слота; отдельно обозначенный профиль 1000 ms меняет только клиентский бюджет опоздания, а серверный дедлайн остаётся прежним. Это разные сценарии, не одна сравнительная ступень.

Новые ресурсы и gzip уменьшают выдачу тела, но требуют декодирования на генераторе. В окончательной паре files 5k тело GET уменьшилось с 11,598 GB до 4,947 GB, средний наблюдавшийся CPU приложения — с 1,99 до 1,69 ядра, генератора — с 1,88 до 3,16. Число ACK немного снизилось; ускорение полного сценария этим сравнением не доказано. Это отдельные последовательные замеры на общей машине, без оценки статистической погрешности.

На files 20k с бюджетом GET 100 ms цепочка массово обрывается до голосования: 429 ACK из 1,2 млн запланированных. В наблюдаемый интервал средний CPU приложения около 0,44 ядра, генератора около 2,08: по этим данным нельзя объявить HTTP-сервер насыщенным по CPU. Таймауты, отмена соединений, лимит workers и общий сетевой стек ноутбука требуют отдельных измерений. Простое увеличение заданного RPS не становится успешной нагрузкой.

В отдельном files-профиле 10k с бюджетом открытия 1000 ms все 2 956 210 начатых GET прошли без ошибок, ACK получили 586 683 из 600 000 попыток. Остались 8758 пропущенных слотов генератора и 4559 поздних отказов. Увеличение клиентского бюджета устранило ошибки начатых цепочек на этой ступени, но не обеспечило полный приём и не даёт прямого сравнения с 20k/100 ms.

Первые диагностические прогоны также сохранены: до повторного использования gzip-декодера на files 5k было 297 820 ACK, на 20k — 404. Отдельный тест выделений памяти показал 41 284 → 48 B на декодирование; он не доказывает рост HTTP-пропускной способности. См. `candidate-provenance.json` и `candidate2-provenance.json`: результаты относятся к разным версиям исходников.

В 23 сохранённых прогонах получено **33 879 753 подтверждений**, потерянных подтверждений — **0**; неопределённых клиентских исходов — **22 738**. Точно сверено 33 879 753; без сверки осталось 0. Один исходный профиль не завершил финализацию автоматически и был сверен после отдельного ручного перезапуска; он остаётся correct=false. Это сумма разных опросов, версий и режимов; не один опрос на 100 млн. Полнота приёма всего плана отражена выше отдельно.

Reader проверяет каждый полный ID, выбор, время допуска и кратность подтверждения, первый сохранённый выбор и итог приложения. Kafka дополнительно проверяется по полному стабильному снимку всех разделов, включая хвост после CLOSED. В обычных успешных прогонах также проверяется неизменность финала после перезапуска; провал и отдельное восстановление описаны ниже. Физическое отключение питания и потеря независимого хоста в этой серии не проверялись.

## Ошибка, найденная заключительной нагрузкой

На Kafka 10k с секундным бюджетом GET пять writer перешли в terminal failure. Финализатор продолжал вызывать Seal на тех же остановленных writer, поэтому результата не было и через 180 секунд. Исходный прогон остаётся проваленным. В журнале Raft в это время есть `BindException: Can’t assign requested address` и смена контроллера. Это согласуется с исчерпанием временных TCP-портов при массовых отменах запросов на общей машине; число занятых портов в пик не измерялось. [Наблюдения](measurements/2026-09-13/review-scale/failed-journey-diagnostics.json).

Отдельный перезапуск прежней версии восстановил финал за 1,45 секунды: все 160 434 ACK совпали с журналом, ещё 14 из 22 738 unknown-попыток оказались сохранены. Итог — 160 448 уникальных. Перезапуск не превратил неуспешную нагрузку в успешную.

Код исправлен: после дедлайна сначала дренируются здоровые разделы, затем старые producers закрываются и присоединяются. После повторной проверки владельца PostgreSQL открывается тот же журнал с fencing и повторяется Seal — максимум одна замена за вызов maintenance. Unknown-попытки не пересылаются и новая минута не начинается. Отмена и потеря владения запрещают повторный захват. Счётчики прежнего writer сохраняются; причины ошибок представлены пятью фиксированными категориями.

Реальная регрессия принудительно отозвала producer epoch одной партиции: здоровая продолжила работать, а после закрытия один вызов FinalizeDue без рестарта получил точный итог 2 ACK → 2 уникальных. ReplayStrict подтвердил выборы и исходное время допуска. Race, vet и независимое повторное ревью нового recovery-перехода пройдены. Во время самой минуты автоматическая замена failed writer пока не выполняется.

## Границы готовности

Файловая ветка по-прежнему имеет одного владельца локального каталога. После I/O-ошибки writer/финализация остаются остановленными до перезапуска и строгой проверки WAL; это касается и временного ENOSPC. Автоматическая замена Kafka producer не переносится на повреждённый диск. Репликация диска и автоматическое переключение на другой узел не реализованы. PostgreSQL/Kafka имеет одного владельца схемы приложения; низкоуровневое владение частью партиций проверяется отдельно и не выдаётся за готовый кластер приложений.

Для подтверждения реального мероприятия нужны нагрузка от независимых машин, выбранная конфигурация сервера приложения, устойчивое хранилище, TLS/CDN, проверка отказов и сверка всех попыток. Требуемая базовая скорость — 1 666 667 уникальных голосов/с; при 10% повторов — 1 833 333 POST/с. Число серверов определяется измеренной ёмкостью такой конфигурации, а не делением цели на результат ноутбука.
