# Нагрузочный стенд настоящего HTTP-голосования

`cmd/httpbench` отправляет отдельный POST на каждый ответ через публичный API работающего приложения. Он проверяет путь HTTP → Repository → файловый sync либо Kafka commit. Это не вызов `SubmitFrame` из генератора: пакет формирует сервер после допуска отдельных запросов.

`scripts/profile_full_http.py` автоматизирует один изолированный минутный опрос: запускает выбранный сервер, создаёт опрос, подаёт нагрузку, получает настоящий окончательный результат, перезапускает приложение и запускает отдельный процесс чтения журнала. Команды ниже описывают процедуру, а не результаты измерений. Расчёт для 100 млн участников приведён в [http-capacity.md](http-capacity.md).

## Подготовка и границы

Сборку выполняйте **до измерения**, в нужной рабочей ветке:

```sh
go build -o bin/gigaquizz ./cmd/gigaquizz
go build -o bin/httpbench ./cmd/httpbench
```

В `simple-files` приложение и reader используют локальный файловый журнал; Kafka-зависимостей в этой команде нет. В `postgres-kafka` reader читает Kafka через `read_committed`, а приложение хранит описание и результат в PostgreSQL. Соберите оба бинарника из соответствующей ветки. Флаг `--mode` у Python-обёртки сам не выбирает другой бинарник; `--runtime-root` определяет каталог данных, а не версию исполняемого файла.

Для обёртки нужны Python 3, `ps`, свободный loopback-порт и локальная POSIX-система с `flock`. Для варианта Kafka дополнительно нужны уже работающие PostgreSQL, три принадлежащих проекту брокера на `127.0.0.1:19092–19094` и `psql`. Подготовка обычного приложения описана в [launch.md](launch.md), Kafka-стенда — в [kafka-lab.md](kafka-lab.md). Обёртка не запускает и не останавливает общие БД или брокеры.

Не выполняйте одновременно другой профиль, сборку или тесты. Все компоненты на одном компьютере делят CPU, память и диск; свободный порт не означает свободные ресурсы машины.

Ограничения локального профиля:

| Параметр | Предел / поведение |
|---|---|
| Окно опроса | Ровно 60 секунд от исходного `starts_at` |
| Новые ID | До 100 000/s; `rate` означает новые ключи, а не все POST |
| Все попытки с повторами | Не более 10 000 000 на прогон |
| HTTP workers | Не более 4096 |
| Свободный диск | Сохраняется резерв 8 GiB; заранее учитывается новый журнал и ledger |
| Существующий Kafka-стенд | Прогноз сохранённых данных вместе с новым профилем должен помещаться в 26 GiB |
| Память Go | Обёртка задаёт `GOMEMLIMIT=3GiB` приложению и `2GiB` генератору; это мягкий предел Go, не жёсткий предел RSS |
| GC / CPU | `GOGC=100`, `GOMAXPROCS` равен числу логических CPU; значения записываются в отчёт |
| Открытые файлы | Только дочерним процессам выставляется soft limit 16384; существующий hard limit должен это позволять |

Оценка диска консервативна и использует старый размер записи, чтобы сравнивать baseline и packed при одном правиле допуска. Это не измеренный физический размер Kafka и не квота файловой системы. Периодическая проверка свободного места может пропустить короткий пик. Старые данные не удаляются: если новый профиль не помещается, уменьшите ступень либо перенесите испытание на подготовленный носитель.

## Автоматический минутный прогон

Из корня `simple-files`:

```sh
python3 scripts/profile_full_http.py \
  --mode simple-files --label files_packed_1000_r5 \
  --server-binary bin/gigaquizz --load-binary bin/httpbench \
  --port 8093 --rate 1000 --repeat-every 5 \
  --workers 256 --queue 4096 --max-lag-ms 100
```

Это 60 000 новых ключей и 12 000 дополнительных попыток за ту же минуту. Значение `--repeat-every 0` отключает повторы. Не запускайте команду повторно с прежним `--label`: каталог должен быть новым.

Для `postgres-kafka` заранее задайте в приватном окружении `TEST_DATABASE_URL` существующей локальной тестовой БД. Пользователю БД нужны права на создание новой схемы. Допускается URL `postgres://` или `postgresql://` с `127.0.0.1`, `::1` либо параметром `host`, указывающим точно на `<runtime-root>/.local`. Обёртка запрещает другие параметры маршрутизации, включая `hostaddr` и `service`; из унаследованного окружения удаляются `PG*`. Пароль не передавайте в CLI и не публикуйте URL подключения.

Из корня ветки `postgres-kafka`, с её бинарниками:

```sh
python3 scripts/profile_full_http.py \
  --mode postgres-kafka --label kafka_packed_1000_r5 \
  --server-binary bin/gigaquizz --load-binary bin/httpbench \
  --port 8094 --rate 1000 --repeat-every 5 \
  --workers 256 --queue 4096 --max-lag-ms 100 --partitions 4
```

Если уже существующий Kafka-стенд находится в другом checkout, добавьте `--runtime-root /absolute/path/to/runtime`. Там должны находиться настоящий `.local/kafka-lab`, его marker и metadata. Не копируйте и не создавайте marker, чтобы обойти проверку владения. По умолчанию `runtime-root` — корень репозитория, содержащего Python-скрипт. Путь `--psql /absolute/path/to/psql` позволяет выбрать установленный клиент явно.

Оба варианта сохраняют данные в `<runtime-root>/.local/http-full-profiles/<label>/`. Внутри будут:

- `service.env`, `poll.json`, `results.json`, `application.log` — приватные конфигурация и данные прогона;
- `ledger/manifest.json` и `ledger/worker-*.bin` — клиентский эталон всех запланированных попыток;
- `load.json`, `audit.json`, `report.json` — агрегаты генератора, независимой сверки и всей процедуры;
- `load.stderr`, `audit.stderr`; для Kafka также `journal-config.json` и отдельная схема `gqhttpfull_*` в БД; для files — `data/polls/.../journal`.

Обёртка резервирует будущий старт: примерно через 8 секунд для files и 35 секунд для Kafka. Это подготовка перед неизменным минутным окном. После нагрузки она ждёт финальный результат, останавливает и заново запускает **свой** сервер, сравнивает сохранённый результат и проверяет `410` на поздний POST. Затем останавливает сервер и запускает независимый reader. Перезапуск здесь штатный; это не проверка SIGKILL, отключения питания или потери узла.

Ожидания ограничены: readiness — 90 секунд, работа генератора — 150, финализация и независимое чтение — по 180. Поэтому весь сценарий дольше одной минуты. При ошибке или Ctrl+C/SIGTERM обёртка останавливает свои дочерние процессы и сохраняет диагностику. Она не продлевает допуск голосов и не удаляет незавершённый журнал. SIGKILL самой обёртки не позволяет выполнить cleanup.

Основные дополнительные флаги обёртки:

| Флаг | По умолчанию | Назначение |
|---|---:|---|
| `--rate` | 1000 | Новые ID/s, 1…100 000 |
| `--repeat-every` | 0 | Дополнительный выбор 2 для каждого N-го ключа; 0 отключает |
| `--journey` | Выключен | Пять последовательных GET перед исходным POST; повторы отправляют только POST |
| `--workers` | 256 | Параллельные HTTP-попытки, 1…4096 |
| `--queue` | 4096 | Очередь генератора, 1…1 000 000 попыток |
| `--max-lag-ms` | 100 | Слот старше этого значения пропускается; 1…1000 ms |
| `--max-inflight` | 4096 | Ограничение одновременно обрабатываемых голосов в приложении |
| `--partitions` | 4 | Только Kafka, 1…32 |
| `--batch-votes` | Не переопределён | Files: группа sync, 1…131 072 голосов; Kafka: 1…4096 |
| `--queue-votes` | Не переопределён | Files: общая очередь до 1 048 576 голосов; Kafka: до 8192 на раздел |
| `--linger-ms` | Не переопределён | Ожидание накопления записи, 1…1000 ms |
| `--app-memory` | `3GiB` | `GOMEMLIMIT` приложения: `2GiB`, `3GiB` или `4GiB` |
| `--cpu-profile` | Выключен | Отдельный диагностический прогон с CPU-профилем каждого запуска приложения |

Параметры хранения без override берутся из выбранного бинарника. Сохраняйте его SHA-256 и настройки: один label «packed» не доказывает, что запущена новая версия. Поля `binary_sha256` находятся в `report.json`.

## Отдельный генератор и повторная сверка

Прямой `httpbench` не создаёт и не останавливает приложение. Нужен отдельный тестовый опрос без посторонних голосов; его исходный старт должен оставаться хотя бы на секунду в будущем. Возьмите точные `id` и `starts_at` из API, не рассчитывайте новое время старта на клиенте.

```sh
umask 077
mkdir -p .local/http-manual
bin/httpbench \
  -url http://127.0.0.1:8093 \
  -poll "$HTTP_POLL_ID" -start-at "$HTTP_POLL_START" \
  -rate 1000 -duration 60s -repeat-every 5 \
  -workers 256 -queue 4096 -max-lag 100ms -request-timeout 12s \
  -ledger-dir .local/http-manual/run_a -allow-high-load \
  > .local/http-manual/load_a.json
```

Здесь `HTTP_POLL_ID` и `HTTP_POLL_START` — заранее заданные значения вашего тестового опроса. Каталог `run_a` должен отсутствовать, его родитель — существовать. Прямой CLI по умолчанию использует **128 workers, очередь 8192 и repeat-every=5**, в отличие от обёртки. Все существенные параметры лучше передавать явно. `-request-timeout` допускает 1 ms…30 s; соответствующего override у обёртки пока нет.

После закрытия сохраните настоящий окончательный ответ `/api/admin/polls/<id>/results` в файл с правами `0600`. Reader принимает этот JSON напрямую либо поле `results` обёртки. Пример повторной проверки уже законченного автоматического files-прогона:

```sh
bin/httpbench \
  -audit-only "$HTTP_RUN/ledger/manifest.json" \
  -file-journal "$HTTP_JOURNAL" \
  -results "$HTTP_RUN/results.json" \
  > "$HTTP_RUN/audit_recheck.json"
```

`HTTP_RUN` — полный путь к каталогу прогона, `HTTP_JOURNAL` — его `data/polls/<id>/journal`. Файловый writer должен быть закрыт: reader использует блокировку и требует полный `CLOSED`.

Для журнала Kafka используйте бинарник `httpbench` из ветки `postgres-kafka`:

```sh
bin/httpbench \
  -audit-only "$HTTP_RUN/ledger/manifest.json" \
  -kafka-config "$HTTP_RUN/journal-config.json" \
  -results "$HTTP_RUN/results.json" \
  > "$HTTP_RUN/audit_recheck.json"
```

Kafka-брокеры должны оставаться доступными, а writer выбранного опроса — быть остановлен: строгая сверка требует неизменяемого журнала без открытых транзакций. Приложение для чтения не требуется. `-file-journal` и `-kafka-config` — альтернативы, reader каждой ветки поддерживает свой backend. `-audit-only` не посылает HTTP, не дописывает journal и не исправляет незакрытый опрос. Неполный manifest после аварии генератора не принимается за полный эталон.

### Сколько места занимает Kafka-журнал

После успешной независимой сверки можно отдельно получить размеры файлов одного опроса. Из checkout `postgres-kafka`:

```sh
umask 077
python3 scripts/kafka_http_disk.py \
  --runtime-root "$HTTP_RUNTIME_ROOT" \
  --kafka-config "$HTTP_RUN/journal-config.json" \
  > "$HTTP_RUN/disk.json"
```

`HTTP_RUNTIME_ROOT` — абсолютный путь к checkout с принадлежащим проекту `.local/kafka-lab`. Helper доступен в ветке `postgres-kafka`; он проверяет marker, metadata и приватную конфигурацию опроса, затем выполняет только `stat` файлов в точных каталогах его разделов. Kafka/PostgreSQL API и содержимое сегментов не читаются. По умолчанию проверка ограничена 20 000 файлов и 10 секундами (`--max-files`, `--timeout`).

`logical_file_bytes` — сумма размеров файлов, `allocated_file_bytes` — сумма `st_blocks × 512`. Оба значения **уже включают три реплики**, повторно умножать на RF3 нельзя. `by_extension` разделяет `.log`, `.index`, `.timeindex`, `.txnindex` и `other`; индексы могут быть предвыделены, а `.log` содержит служебные записи, транзакционные маркеры и сохранённые отменённые данные. Каталоги учитываются отдельно в `allocated_directory_bytes`. Общие внутренние топики, broker logs и checkpoints за пределами этих каталогов исключены.

Это неатомарный снимок текущего хранения, а не полезные байты голосов, пиковый расход диска или доказательство ACK/ISR. Сжатие файловой системы и общие экстенты также ограничивают трактовку allocated bytes как исключительно занятого физического места. Поэтому `closed_barriers_verified=false` в этом отчёте ожидаемо: полноту `CLOSED` доказывает отдельный reader.

## Что именно измеряется

План для `r` новых ключей/s и повторов через `e` ключей:

`U = 60r`; `A = U`, если `e=0`, иначе `A = U + floor(U/e)`.

Уникальные ключи размещены равномерно в исходной минуте. Генератор следует расписанию независимо от скорости ответов, имеет ограниченные очередь и число workers и сохраняет пропущенные слоты в знаменателе. Он может объединять пробуждения примерно до 1 ms. Это не гарантирует, что каждый запланированный запрос успеет уйти по сети.

Исходная попытка выбирает вариант 1, дополнительная — вариант 2 с тем же полным токеном. Дополнительная попытка отправляется конкурентно и иногда может попасть в журнал раньше исходной. Эталон учитывает **первое появление ключа в журнале**, а не заранее предполагает итог «все выбрали 1».

По умолчанию прогон измеряет отдельные POST с переиспользованием соединений и один раз проверяет описание опроса перед нагрузкой. Режим journey ниже добавляет запросы страницы и ресурсов для каждого нового ключа. Оба режима не исполняют JavaScript, не используют IndexedDB и не моделируют CDN, географию или массовые новые соединения. На loopback-адресе обёртки нет TLS; поддержка HTTPS у прямого клиента сама по себе не моделирует отдельное TLS-соединение каждого браузера.

`load.json`:

| Поле | Как читать |
|---|---|
| `planned_unique_keys`, `planned_attempts` | Разные знаменатели: участники и все попытки с повторами |
| `http_post_sent` | Попытки HTTP-вызова генератором; это не счётчик запросов, принятых сервером |
| `valid_recorded_ack` | Валидные `202 recorded`, включая повторы; не число уникальных голосов |
| `generator_skipped` | Слот не отправлен: очередь/lag/отмена; это предел генератора, не потеря ACK в хранилище |
| `journey_failed` | Исходная попытка начала цепочку GET, но та завершилась ошибкой или не уложилась в бюджет; POST не отправлен |
| `not_admitted` | Явный `503` с `outcome=not_admitted`; запись не допущена |
| `closed`, `not_open` | Явные `410` и `425`; не считать их потерянными подтверждёнными записями |
| `unknown` | Timeout, ошибка транспорта или неоднозначный ответ; запись могла сохраниться |
| `rejected` | Прочие распознанные окончательные отказы API |
| `invalid_successful_responses` | Невалидные положительные ответы; это ошибка контракта, а не допустимый успех |
| `complete`, `cancelled` | Полнота клиентского ledger и отмена; `complete=true` не означает 100% ACK |

При полном прогоне сумма `ACK + unknown + closed + not_admitted + not_open + rejected + skipped + journey_failed` равна `planned_attempts`. Отчётная производительность за событие — `valid_recorded_ack / 60`; отдельно приводите `valid_recorded_ack / planned_attempts` и итоговую долю `canonical_unique_keys / planned_unique_keys`. Время drain не заменяет фиксированный знаменатель 60 секунд.

Поля `latency_*_upper_bound_ms` — верхние границы степенных интервалов гистограммы, а не точные процентили. Они и средняя задержка считаются от начала HTTP-вызова до завершения ответа/ошибки **по всем отправленным POST**. Ожидание исходного слота, очередь и предшествующие GET в эти значения не входят; это также указано в `post_latency_scope`. В текущей реализации массивы `post_sent_per_scheduled_second` и `ack_received_per_scheduled_second`, несмотря на название, распределены по фактическому времени отправки/получения относительно старта. Завершения после 60-й секунды входят в общие счётчики, но не в эти 60 элементов.

Нельзя складывать весь `1 − ACK/A` в одну «потерю данных». Это доля попыток без валидного подтверждения; её причины видны в отдельных полях. Допуск на 59,9 секунды с ответом после закрытия корректен, если время серверного допуска сохранено в исходном окне.

## Journey: загрузка ресурсов перед голосом

Добавьте `--journey` к команде обёртки, задав новый label, либо `-journey` к прямому `bin/httpbench`. В `load.json` появится `mode="http-journey"`, а в конфигурации обёртки — `journey=true`. По умолчанию остаётся `http-post`.

Перед каждой исходной попыткой с выбором 1 worker последовательно запрашивает:

1. `/p/<id>` — HTML;
2. `/static/app.css`;
3. `/static/common.js`;
4. `/static/poll.js`;
5. `/api/polls/<id>` — описание того же опроса.

Только после успешной цепочки он отправляет POST. Дополнительная попытка с выбором 2 выполняет только POST и может попасть в журнал раньше исходной. `rate` по-прежнему задаёт новые ключи/s: при успешной загрузке план добавляет `5U` GET к `A` POST. Это план, а не гарантия фактического числа запросов.

Каждый GET выполняется заново без браузерного кеша, но JavaScript не исполняется. Ресурсы загружаются последовательно, а не параллельно, как это может делать браузер. Используются те же ограниченные workers и общий пул соединений: цепочка GET занимает worker до перехода к POST. Никакой отдельной неограниченной очереди загрузчиков нет. Серверные кеши этим режимом не отключаются.

Вся цепочка должна завершиться до `исходный слот + max-lag`: при настройках по умолчанию это 100 ms, включая уже потраченное ожидание в очереди. Это общий бюджет перед POST, а не 100 ms на каждый GET. Ошибка либо истечение бюджета оставляет попытку в знаменателе как `journey_failed`; её POST не отправляется. Просроченный слот, отброшенный ещё до начала цепочки, относится к `generator_skipped`. Собственный timeout отправленного POST остаётся прежним, а минутную границу допуска по-прежнему проверяет сервер.

Для каждого GET требуются `200`, непустое тело, подходящий `Content-Type` и отсутствие сжатого `Content-Encoding`; JSON вопроса также проверяется на соответствие исходному опросу. Предел тела — 256 KiB для каждого HTML/CSS/JS и 64 KiB для JSON. Для обнаружения превышения читается максимум один дополнительный байт. Статические тела читаются потоково, JSON сохраняется только в указанном пределе.

В `load.json` доступны:

| Поле | Как читать |
|---|---|
| `journey_started`, `journey_completed_before_post` | Начатые цепочки GET и цепочки, успешно завершённые в бюджете |
| `http_get_sent`, `http_get_failures` | Вызовы GET клиентом и неуспешные начатые GET |
| `http_get_body_bytes` | Фактически прочитанные байты тел, включая прочитанное при ошибках |
| `http_get_stages` | Счётчики, байты, средняя и максимальная задержка по стадиям `html`, `css`, `common_js`, `poll_js`, `question` |
| `journey_mean_ms`, `journey_max_ms` | Время цепочки GET, включая неуспешные цепочки; без очереди и POST |

В этих GET-метриках нет единственной подготовительной проверки опроса, заголовков и транспортных расходов. Вызовы `client.Do` не раскрывают возможное прозрачное восстановление GET-соединения внутри Go Transport. `http_get_failures` не обязано равняться `journey_failed`: бюджет может истечь между GET, когда следующий запрос ещё не начат. В независимом аудите такие попытки видны как `journey_failed_client_attempts`; они не могут объяснять запись в серверном журнале, поскольку их POST не выполнялся.

## Независимая точная сверка

Reader проверяет CRC каждой 64-байтовой записи ledger, SHA-256 всех его файлов, полноту расписания, все 128 бит токена, выбор и исход каждой попытки. Затем последовательно читает серверный журнал с проверкой закрытия и его хвоста по правилам backend ниже. Для каждого ACK должно существовать ровно одно совпадение `token + choice + admitted_at`. Дополнительные записи голосов допустимы лишь для попыток с исходом `unknown`; повторная физическая копия одной попытки — ошибка.

Файловый путь использует прежний `filelog.Replay`: writer закрыт, полный `CLOSED` обязателен, любые байты после него — ошибка. Kafka-путь независимого аудита использует `ReplayStrict`, а production-финализация и восстановление по-прежнему читают префикс до `CLOSED` через `Replay`.

`ReplayStrict` требует остановленной записи, отсутствия compaction и сохранённого начала каждого раздела с offset 0. Он фиксирует границы HW и LSO и требует `HW == LSO`: незавершённая транзакция не позволяет объявить снимок полным. Чтение проходит до всей зафиксированной границы, включая продвижение по offsets транзакционных маркеров и отменённых batches; пустой видимый fetch сам по себе не доказывает окончание. После чтения повторно проверяются идентичность топика, лидеры/epochs и границы разделов. Изменение снимка, timeout или непрочитанный хвост означают неуспешную сверку.

После `CLOSED` запрещены подтверждённые транзакцией голоса/frames и повторный `CLOSED`. Допустимы корректные служебные `BOOT` восстановления: они полностью проверяются по неизменяемой конфигурации и считаются отдельно, без добавления голосов. Проверка доказывает содержимое этого стабильного снимка, а не невозможность любых будущих записей.

AES-перестановка со случайными seed и namespace позволяет восстановить номер синтетического ключа без огромной map. Это точная проверка полного ключа; SHA-256 используется для целостности ledger, а не как вероятностный заменитель дедупликации. Первый journal occurrence каждого ключа считается независимо и сравнивается с сохранённым окончательным результатом настоящего приложения.

В `audit.json` проверяйте:

- `correct`, `ledger_valid`, `journal_closed`, `saved_service_results_matched` должны быть `true`;
- `matched_ack_attempts == confirmed_attempts`, `missing_ack_attempts == 0`, `unverified_ack_attempts == 0`;
- `unexpected_records`, `unexpected_physical_copies`, `receipt_mismatches`, `invalid_successful_responses` должны быть нулевыми;
- `unknown_attempts_found_committed` показывает, сколько неизвестных клиенту попыток реально обнаружено; `canonical_unique_keys` и `canonical_choice_counts` — итог после точного удаления повторов.
- Для Kafka дополнительно требуются `journal_inspection.strict_snapshot_complete=true` и `journal_inspection.snapshot_partitions`, равное числу разделов; `journal_inspection.recovery_boot_records` показывает число допустимых `BOOT` после закрытия. В files это Kafka-поле отсутствует.

Если чтение оборвалось до полного `CLOSED` либо строгая проверка Kafka-снимка не закончена, `unverified_ack_attempts` означает «ещё не проверено», а не доказанную потерю. Только законченная сверка может назвать ACK отсутствующим. `report.json.correct=true` подтверждает сверку и перезапуск, но совместимо с пропусками генератора и отказами в допуске: успешность обслуживания оценивается отдельно.

## Сравнение baseline и packed

Сохраните старый серверный бинарник до изменения исходников. Одной версией генератора выполните одинаковые ступени против старого и нового сервера; передавайте `--server-binary` явно и используйте разные label. Сравнивайте одинаковые rate, repeats, workers, queue, max-lag, режим journey, настройки хранения, число разделов и CPU/память. Не смешивайте эффект упаковки с одновременным увеличением всех очередей или добавлением GET.

Baseline уже группировал sync/транзакции, но хранил отдельную физическую запись на одиночный запрос. Packed объединяет допущенные одиночные запросы на сервере, сохраняя индивидуальные времена допуска и подтверждая их только после прежней границы сохранения. Размер записи и количество физических frames следует проверять по журналу/метрикам, а ускорение — по одинаковым HTTP-прогонам. Сам факт уменьшения байтов не гарантирует рост RPS.

Начинайте с небольшой ступени, затем повышайте rate по одному изменению, например 1000 → 5000 → 20 000 → 50 000 → 100 000 новых ID/s при достаточном запасе. Повторите интересующие сравнения: один прогон не доказывает устойчивый предел. Высокие skips при загруженном генераторе не позволяют приписать предел только серверу. Большая очередь может убрать краткий провал, но не исправляет длительный дефицит скорости и повышает задержку около закрытия.

В `report.json.samples` есть роли процессов, фаза, монотонное прошедшее время, накопленное CPU-время и RSS. Для Kafka добавляются только PID, проверенные по metadata принадлежащего проекту стенда. Сравнивайте фазу `workload` отдельно от `preparation`, `drain`, `final_result` и `independent_reader`. Сэмплы примерно раз в секунду не гарантируют фиксацию краткого пика; отсутствие процесса в сэмпле не равно нулевому потреблению. Встроенные сэмплы не измеряют весь I/O, PostgreSQL и внешнюю сеть. Не делайте из них вывод о свободной мощности всех зависимостей.

### Версия генератора в сохранённых POST-прогонах

Текущие парные POST-прогоны baseline/packed используют сохранённый генератор v1. В нём проверка выбора из ACK предварительно сужала число до `uint32`: специально некорректное большое или отрицательное значение могло превратиться в 1 или 2. В актуальных исходниках сравнение выполняется без сужения и добавлены отрицательные тесты. Контролируемое приложение возвращает только варианты 1/2; неверный ACK из-за этой ошибки в прогонах не наблюдался. Тем не менее исправленные исходники не являются исходной версией измеренного бинарника: сохраняйте его SHA-256 и эту оговорку вместе с результатами.

Старый Kafka-reader проверял префикс до первого `CLOSED` каждого раздела и не доказывал отсутствие записей после этого барьера. Все шесть сохранённых Kafka HTTP-профилей baseline/packed повторно проверены новым строгим reader: в каждом `correct=true`, `journal_inspection.strict_snapshot_complete=true`, пропущенных ACK нет, служебных `BOOT` после закрытия — 0. Всего повторно сопоставлено 1 312 448 ACK. Это отдельная проверка сохранённых журналов; она не меняет версию генератора и исходные показатели нагрузки. Старые отчёты сохраняются вместе с повторными аудитами.

## Отдельная диагностика CPU

Добавьте `--cpu-profile` к отдельному прогону обёртки с новым label, например `files_cpu_1000_r5`. Нужен серверный бинарник, поддерживающий `-cpu-profile`; сохранённый baseline до появления этого флага для такой диагностики не подходит. Флаг не включается по умолчанию.

В приватном каталоге появятся `cpu-1.pprof` для первого запуска и `cpu-2.pprof` для проверки после перезапуска. Каждый файл охватывает всю жизнь соответствующего процесса: запуск, подготовку, обслуживание, финализацию и остановку, а не только минуту допуска. Генератор и независимый reader этим флагом не профилируются. В `report.json` такой прогон помечен `diagnostic_cpu_profile=true`.

Диагностический прогон **исключайте из сравнения baseline/packed RPS и задержек**: сбор CPU-профиля добавляет затраты. Его задача — показать, где тратится CPU. Разбирайте профиль после окончания нагрузок и с тем же серверным бинарником:

```sh
go tool pprof -top /absolute/path/to/measured/gigaquizz "$HTTP_RUN/cpu-1.pprof"
go tool pprof -top -cum /absolute/path/to/measured/gigaquizz "$HTTP_RUN/cpu-1.pprof"
```

Доли CPU-сэмплов не равны долям wall-clock задержки запроса: ожидание диска или сети может занимать много времени без расхода CPU. Не приписывайте весь профиль пути POST, если значимую часть работы составили startup или точный пересчёт результата. Профили сохраняются вместе с приватными артефактами; при аварийном убийстве приложения файл может оказаться неполным.

## Приватность и цель 100 млн

Ledger содержит полные случайные токены, seed/namespace для их восстановления, выбор, время и исход каждой попытки. `service.env` содержит пароль администратора, а в Kafka-режиме — параметры БД. Это приватные артефакты испытания: каталоги `0700`, файлы `0600`, размещение в `.local`, без публикации в git. IP и fingerprint генератор не собирает. Для публикации используйте проверенные агрегаты, не весь каталог и не сырые журналы. Сохраняйте артефакты до окончания сверки/разбора; автоматического удаления нет.

Этот локальный CLI намеренно не допускает полный профиль 100 млн HTTP-попыток. Только клиентские записи такого события заняли бы `100 000 000 × 64 = 6,4 GB`; с 20% повторов — 7,68 GB, сверх серверного журнала, реплик, результатов и запаса. Компактное состояние reader требует примерно `9A + U` байт, а память точного production-пересчёта полного набора ключей считается отдельно.

Для 100 млн участников за минуту нужен план распределённой генерации, независимые пространства синтетических ключей, единое исходное расписание, полные приватные ledger всех генераторов и общая сверка результата. Эти возможности не включаются существующим флагом. Вынос генераторов на отдельные машины также позволяет отделить их предел от сервера. Результат пакетного ядра на 1,7 млн логических попыток/s не заменяет этот HTTP-тест и не определяет необходимое число production-серверов.
