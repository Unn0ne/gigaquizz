Эксперимент с хранилищем: пропускная способность, квитанции и сохранность.

`go run ./cmd/storagebench` вызывает настоящий `postgres.Store.Vote` в отдельной случайной схеме PostgreSQL. Измеряется путь драйвера и БД; HTTP, браузер, CDN, административная аутентификация и проверка HTTP-body в эксперимент не входят. Проверки API выполняются отдельно. Этот инструмент не подтверждает 100 млн голосований за минуту и не создаёт облачных ресурсов.

По умолчанию: 100 логических ключей, 100 ключей/с, 16 работников, очередь 64. Расписание занимает одну секунду; затем CLI **дожидается настоящего закрытия опроса через 60 секунд**, выполняет штатную финализацию и сверяет каждую запись. Время нагрузки и полное время команды выводятся отдельно. Дедлайн опроса, `starts_at` и `finalized_at` ради ускорения проверки не изменяются.

Подготовить [локальную БД по README](../README.md) либо [стенд с primary и двумя standby](replication-lab.md). Стенд работает на одном компьютере: общие диск, CPU и питание не моделируют независимость зон. Для репликационного стенда:

```sh
python3 scripts/replication_lab.py up
python3 scripts/replication_lab.py status
export STORAGEBENCH_DATABASE_URL="$(python3 -c 'import json; print(json.load(open(".local/replication-lab/metadata.json"))["primary_url"])')"
go run ./cmd/storagebench \
  -required-standbys 1 \
  -standby-names gigaquizz_ha_a,gigaquizz_ha_b \
  -retain-schema
```

URL принимается **только** через `STORAGEBENCH_DATABASE_URL`: CLI не читает автоматически `.env` и не выводит URL или пароли. После promotion заново получить актуальный URL из metadata. Нужен прямой адрес выбранного primary, без балансировщика между несколькими владельцами. Для обычной одиночной локальной БД задать её URL в этой переменной и опустить параметры standby. Нулевой quorum разрешён только когда сервер не настроен на синхронные standby; несовпадение политики завершается ошибкой.

Вместо флагов можно задать `STORAGEBENCH_REQUIRED_STANDBYS` и `STORAGEBENCH_STANDBY_NAMES`. Стенд использует `ANY 1 (gigaquizz_ha_a,gigaquizz_ha_b)`; имена и порядок должны совпадать с серверной политикой. `NewWithOptions` и `WaitDurable` проверяют требуемый flush и идентичность primary; подробности и ограничения — в [описании проверки сохранности](replication-durability.md). Доступность сервера или успешный SQL-ответ сами по себе не заменяют эту проверку.

Каждый прогон создаёт `gqbench_<16 hex>` и устанавливает `search_path=<эта схема>,pg_catalog` для **всех** своих соединений. `public` и другие прикладные схемы в путь поиска не входят. Миграция, опрос, голоса, маркеры и результат создаются только в этой схеме; разрешение `CREATE SCHEMA` и доступ к диагностическим представлениям требуются заранее. Глобальные настройки PostgreSQL, replication slots, checkpoints и внешний стенд CLI не меняет.

Нормально завершённая временная схема удаляется. `-retain-schema` сохраняет её и создаёт отдельный приватный JSON-ledger искусственных ключей в `.local/storagebench/` с правами 0600. `-audit-file` позволяет выбрать **новый** путь файла; существующий файл не перезаписывается. После ошибки уже начатого опыта схема сохраняется для исследования, по возможности сохраняется и ledger. Ошибка удаления отражается отдельно в JSON. Все тестовые схемы имеют случайное имя; схема из ledger проверяется по строгому шаблону перед обращением к БД.

Примеры небольших профилей на репликационном стенде:

```sh
# Один опрос, 1000 ключей за 5 секунд; повтор каждого второго ключа.
go run ./cmd/storagebench -total 1000 -rate 200 -repeat-every 2 \
  -required-standbys 1 -standby-names gigaquizz_ha_a,gigaquizz_ha_b

# Тот же профиль, но конкурентная повторная попытка выбирает другой вариант.
go run ./cmd/storagebench -total 1000 -rate 200 -repeat-every 2 -different-choice \
  -required-standbys 1 -standby-names gigaquizz_ha_a,gigaquizz_ha_b \
  -retain-schema
```

Без пропусков это 1000 логических ключей и 1500 попыток. При одинаковом выборе ожидаются 1000 `accepted` и 500 `duplicate`; при разных — 1000 `accepted` и 500 `conflict`. Победителем может стать любой из двух отправленных выборов, в зависимости от порядка атомарного принятия. Сверка проверяет, что фактическое содержимое совпадает с отправленным и подтверждённым выбором, а число голосов остаётся 1000. Это ожидания теста, не заранее объявленный результат.

Повтор — отдельная работа, поставленная в ту же очередь в момент исходного слота. Работники могут исполнять обе попытки одновременно; при одном работнике конкурентность отсутствует. При переполнении очередь может принять только одну попытку пары, что отражается в счётчиках. Нет goroutine на каждый ключ и нет скрытых повторов при ошибке.

Расписание открытое: ключ `i` назначается на `start+i/rate` по монотонным часам. Замедление БД не переносит будущие слоты. Очередь и число работников ограничены, устаревшие слоты пропускаются и считаются. `-max-lag` по умолчанию 100 мс; `-timeout` — 3 секунды на вызов; `-drain-timeout` — до 10 дополнительных секунд после расписания. Незавершённые вызовы после отмены могут иметь неизвестный серверный исход, поэтому окончательная сверка ждёт реального барьера закрытия.

Жёсткие ограничения: не более 500000 ключей, максимум один повтор на ключ, окно `total/rate` не более 55 секунд, 256 работников, очередь 8192, `-max-lag` до 1 секунды, тайм-аут вызова до 10 секунд и дополнительное завершение до 15 секунд. Больше 10000 ключей либо среднего потока с повторами выше 1000 попыток/с требует `-allow-large`; этот флаг не снимает жёсткие пределы. Ключи и отдельные времена попыток хранятся в памяти в пределах заданного максимума; допустимый размер приватного ledger ограничен 128 МиБ. Наблюдения не предназначены для хранения 100 млн ключей в одном процессе.

Длинное окно нагрузки не продлевает реальную минуту опроса: подготовка после его создания и очередь расходуют её часть. Попытка может дойти до проверки допуска после закрытия и получить `closed`; дополнительные секунды drain позволяют дождаться вызовов, но не разрешают поздние голоса.

`-warm-connections` заранее открывает и проверяет все соединения репозитория через `Store.Warm`, включая проверку сохранности, **до создания опроса**. По умолчанию флаг выключен, чтобы сохранять возможность сравнения с холодным пулом. Он разрешён только для `-mode vote`; `blind` использует отдельный insert pool и отклоняет этот флаг, как и `-audit-only`. Прогрев соединений не означает прогрев всех данных, индексов или состояния дискового кеша. Значения `max_lag_ms`, `timeout_ms`, `drain_timeout_ms` и `warm_connections` записываются в `configuration`.

JSON разделяет следующие группы:

| Группа | Смысл |
|---|---|
| `configuration`, `database` | Настройки профиля и проверяемые параметры БД без URL/пароля |
| `workload.logical_*` | Запланированные ключи, обработанные слоты, ключи с отправленными попытками, неподтверждённые и подтверждённые ключи |
| `workload.attempts_*` | Запланированные, поставленные в очередь, отправленные, пропущенные и не дошедшие до расписания попытки |
| `outcomes` | Квитанции `accepted`, `duplicate`, `conflict`, другие статусы и ошибки с неизвестным исходом |
| `dispatch_lag` | Задержка генератора относительно назначенного слота |
| `database_call_latency` | Полный вызов драйвера, включая получение соединения и доказательство требуемой сохранности |
| `attempt_end_to_end_from_schedule` | От назначенного слота до завершения каждой попытки; учитывает очередь генератора |
| `first_client_confirmation_from_schedule` | До первой полученной `accepted`/`duplicate` для ключа; один ключ учитывается один раз |
| `first_confirmation_deadline_counts_from_schedule` | Число ключей, первое подтверждение которых получено позднее 100/250/500/1000 мс от исходного слота; неподтверждённые ключи указаны отдельно |
| `workload.one_second_buckets` | Расписание, отправки, ответы `accepted`, неизвестные исходы, первые подтверждения и причины пропусков по секундам |
| `wal`, `physical_sizes` | Отдельные границы журнала и выделенного места таблиц, с описанием метода |
| `reconciliation` | Проверка каждой строки/ключа, содержимого квитанций и окончательных агрегатов |

«Клиент» здесь — Go-генератор БД, не браузер и не HTTP-клиент. Квитанция `conflict` учитывается как отдельный исход; она не превращается в подтверждение другого отправленного выбора. Ранее подтверждённый ключ не учитывается второй раз при `duplicate`. Ошибка/тайм-аут не означает, что голос потерян: строка может существовать, но вызывающая сторона не получила доказанного подтверждения.

Все распределения содержат число наблюдений, среднее и точные p50/p95/p99 по правилу ближайшего ранга. Перцентили вычисляются из всех наблюдений одного ограниченного прогона; p99 работников не усредняются. Время вызовов включает ошибки, а распределение первого подтверждения содержит только подтверждённые ключи. Для объединения независимых прогонов нужна общая выборка либо совместимые корзины: среднее их p99 не является общим p99.

Счётчики `after_100_ms`, `after_250_ms`, `after_500_ms`, `after_1000_ms` накопительные и используют строгое превышение порога. Например, ключ с первым подтверждением через 600 мс входит в первые три счётчика. Берётся самый ранний момент завершения корректного `accepted`/`duplicate` одного ключа, включая конкурентные повторы; порядок захвата блокировки метрик не меняет этот выбор. `planned_keys_without_confirmation` включает и неотправленные ключи. Увеличение очереди или `-max-lag` не скрывает ожидание: исходный назначенный слот остаётся началом этого измерения.

`workload.started_at` и `finished_at` — UTC-границы выполнения `runWorkload`: начало до запуска работников и конец после завершения их вызовов, до расчёта перцентилей. Они предназначены для совмещения с внешними CPU/WAL/wait-event наблюдениями. Длительности и секундные корзины используют монотонные часы; при корректировке системного времени длительность остаётся надёжнее разности UTC-меток. Корзина `start_second=s` покрывает `[s,s+1)` относительно начала нагрузки:

| Поле корзины | Момент отнесения к секунде |
|---|---|
| `logical_scheduled`, `attempts_scheduled` | Исходный назначенный слот ключа, включая повтор |
| `skipped_by_reason` | Тот же исходный слот; причина отражает последующий отказ генератора или работника |
| `attempts_sent` | Отметка непосредственно перед учётом отправки и вызовом репозитория |
| `accepted_responses`, `unknown_outcomes` | Отметка сразу после возврата вызова репозитория |
| `first_client_confirmations` | Самое раннее корректное положительное завершение каждой логической операции |

Поэтому корзины показывают отдельно расписание и фактическую активность: пропуск, обнаруженный на следующей секунде, относится к исходному слоту, а поздний ответ — к секунде получения. `database_call_latency` также включает короткий участок учёта отправки непосредственно перед вызовом репозитория. Хранилище временных корзин фиксировано: максимум 128; последняя корзина, `start_second=127` и `includes_later_seconds=true`, собирает все более поздние события, если сам процесс был надолго приостановлен.

`attempts_started_during_window_per_scheduled_second` использует только начала попыток внутри окна и заданную длительность. `attempts_per_workload_second` учитывает всё время нагрузки с завершением хвоста. `total_wall_seconds` дополнительно включает подготовку, настоящее ожидание конца минуты, финализацию и удаление. Низкая достигнутая скорость при пропусках показывает предел генератора/системы, а не выполнение заданного профиля. Код завершения 0 не обещает целевой RPS или отсутствие пропусков; обязательно читать счётчики.

Методика измерения WAL:

1. Создать схему и пустой набор таблиц, опрос и маркер `before`. Подтвердить его через `WaitDurable`; снять `pg_current_wal_insert_lsn()` и `pg_current_wal_flush_lsn()` до нагрузки.
2. После завершения клиентских вызовов снять позицию WAL и размеры таблиц. Файл ключей и служебные запросы также требуют времени; это наблюдаемая граница после client drain, а не точный момент последнего commit.
3. Записать отдельный маркер `after_drain`, выполнить `WaitDurable` и снова снять insert/flush позиции. Его запись включена во вторую дельту, явно отделённую от первой.
4. Вычислить разности через `pg_wal_lsn_diff`. Финализация и удаление схемы идут позже и не входят в эти дельты.

LSN относится ко **всему primary**, поэтому фоновая или чужая нагрузка загрязняет оценку. Позднее разрешение неизвестных операций может оказаться после первого снимка и даже после маркера; он подтверждает достигнутый префикс, а не останавливает все писатели. Нельзя делить первую дельту на `accepted` и выдавать её за точную физическую цену голоса. Для чистого сравнения нужен отдельный спокойный кластер, одинаковые checkpoint/cache conditions и зафиксированная доля неизвестных операций. Команда не вызывает `CHECKPOINT` и не меняет параметры сервера ради удобного результата.

Размеры снимаются через `pg_total_relation_size` обычных таблиц из изолированной схемы, включая их индексы/TOAST. Для голосов отдельно суммируются 32 листовые таблицы `votes_p*`. Вычитается размер пустой схемы до нагрузки; повторный снимок делается после реальной финализации. Это выделенные байты relations, **не** WAL, объём физических записей на диск или измерение flush latency. Разница может быть нулевой на маленьком опыте из-за уже выделенных страниц.

Окончательная сверка выполняется в read-only repeatable-read snapshot после штатного закрытия:

- Для каждой строки проверяется, что токен принадлежит прогону и хотя бы одна попытка этого ключа действительно отправлялась.
- Выбор должен входить в отправленные варианты и совпадать со всеми наблюдавшимися положительными квитанциями/квитанциями конфликта.
- Каждый клиентом подтверждённый ключ должен существовать. Несколько `accepted` одного ключа фиксируются как ошибка, даже если уникальный индекс оставил одну строку.
- Неопределённые неподтверждённые ключи отдельно распределяются на найденные и отсутствующие после закрытия. Их отсутствие не называется потерей подтверждённой записи.
- Общий итог и счётчики вариантов из `poll_results` сравниваются с исходными строками. Совпадение одной суммы не заменяет проверку множества ключей и содержимого.

Стабильность проверяется по видимому результату настоящего барьера; ожидание фиксированных нескольких секунд вместо него не используется. При недоступности БД/финализации отчёт не объявляет сверку успешной. Ошибочный эксперимент сохраняет схему и ledger для дальнейшего восстановления, если это технически возможно.

Для повторного аудита после управляемого отказа и смены primary:

```sh
# Сначала выполнить действия контроллера из replication-lab.md и восстановить
# требуемую сохранность. Указать путь из private_key_ledger_file предыдущего JSON.
export STORAGEBENCH_DATABASE_URL="$(python3 -c 'import json; print(json.load(open(".local/replication-lab/metadata.json"))["primary_url"])')"
go run ./cmd/storagebench -audit-only .local/storagebench/gqbench_ИМЯ_ПРОГОНА.json \
  -required-standbys 1 -standby-names gigaquizz_ha_a,gigaquizz_ha_b
```

`-audit-only` не создаёт схему, не пишет голоса, не финализирует опрос, не переключает primary и ничего не удаляет. С положительным `-required-standbys` он открывает репозиторий с этой политикой, после per-key snapshot повторно читает и сверяет `Store.Results`, затем выполняет `WaitDurable`; успех отражается как `explicit_replication_durability_checked=true`. Требуется прямой адрес одного фиксированного primary: контроль его эпохи не заменяет внешний fencing. Без положительной политики инструмент проверяет только наблюдаемую копию, в том числе уже финализированный standby; поле проверки репликации остаётся `false`.

Если исходный прогон оборвался до финализации, сначала её должен безопасно завершить восстановленный сервис; отсутствие барьера не подменяется нулевым итогом. Ledger находится вне БД: потеря данных primary не может одновременно удалить единственное свидетельство полученных клиентом подтверждений. Ledger содержит только синтетические тестовые ключи; его нельзя публиковать как обычный лог или использовать для реальных участников.

Для исследования цены базового пути есть отдельный контроль:

```sh
go run ./cmd/storagebench -mode vote -total 1000 -rate 500 \
  -required-standbys 1 -standby-names gigaquizz_ha_a,gigaquizz_ha_b
go run ./cmd/storagebench -mode blind -total 1000 -rate 500 \
  -required-standbys 1 -standby-names gigaquizz_ha_a,gigaquizz_ha_b
```

Оба режима используют одинаковые поля, таблицу с теми же partition/unique/FK constraints и требуемый durable ACK. Контроль выполняет безусловный INSERT уникального нового ключа в небольшой SQL-обёртке с тем же admission-lock и проверкой окна: это сохраняет возможность корректного барьера закрытия. Повторы в `blind` запрещены. Полная валидация выбора, `ON CONFLICT`, восстановление прежней квитанции и часть пути репозитория отсутствуют; контроль использует отдельный insert pool и публичный `WaitDurable` на том же фиксированном primary. Поэтому отношение производительности этих двух режимов **не является стоимостью дедупликации**. Для её выделения нужен следующий эксперимент с полностью одинаковой валидацией, распределением соединений и единственным изменением условности записи.

Без `-warm-connections` начальный `Ping` не доказывает прогрев всех соединений пула; создание дополнительных соединений может попасть в измерение. Для сравнения учитывать одинаковые версии, оборудование, состояние кеша, checkpoint, объём данных, параметры durable ACK и долю повторов. Сначала нужны несколько небольших воспроизводимых профилей и диагностика генератора; дорогой масштабный прогон требует отдельно согласованных плана и бюджета.

Проверки самого инструмента:

```sh
go test -race ./cmd/storagebench
```

Они проверяют пределы памяти/нагрузки, pinning search_path, bounded queue и пропуски, конкурентные разные выборы одного ключа, точные квантили, границы секундных корзин, порядок первых подтверждений и приватный ledger без перезаписи. Работа реальной БД и репликации проверяется отдельными небольшими прогонами, не имитируется этими unit-тестами.
