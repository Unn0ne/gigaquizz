Как запустить Gigaquizz

В репозитории есть работающий сайт на Go/PostgreSQL и отдельные нагрузочные инструменты. Сайт позволяет создать опрос, проголосовать и посмотреть результат. Эксперименты с RAM-ядром и Kafka проверяют будущий массовый путь; выбор такого режима в интерфейсе сайта пока не реализован. Запуск сайта не включает Kafka автоматически.

Локальный сайт

Потребуются Go 1.26.1+, Python 3, `make` и PostgreSQL 16+ либо Docker с Compose. Для сайта не нужны Java, Kafka, Node.js и сборка фронтенда: HTML/CSS/JS встроены в Go-бинарник. Для нагрузочных Python-скриптов используйте Python 3.12+ (либо Python 3.11.4+).

```sh
cd /Users/makariusiii/Unn0ne/gigaquizz
make dev
```

На другом компьютере используйте свой путь к репозиторию. Скрипт найдёт PostgreSQL в PATH или Postgres.app; если его нет, запустит БД через Docker Compose. При первом запуске создаются изолированная локальная БД и `.env` со случайным паролем администратора. Уже существующие настройки и данные сохраняются. Приложение запускается в текущем терминале; остановка — Ctrl+C. БД после этого остаётся для следующего запуска.

Откройте адрес `PUBLIC_URL` из `.env`, затем `/admin`. По умолчанию это `http://127.0.0.1:8080/admin`; на текущем рабочем компьютере настроен `http://127.0.0.1:8088/admin`. Пароль находится в `ADMIN_PASSWORD` того же файла. Через кабинет создайте вопрос, задайте варианты и время начала, затем откройте ссылку участника в отдельном браузерном контексте. Один опрос принимает голоса ровно 60 секунд; первый принятый выбор браузерного ID окончательный.

Если порт занят, задайте свободный порт одновременно в `HTTP_ADDR` и `PUBLIC_URL`, например `127.0.0.1:8088` и `http://127.0.0.1:8088`. Повторно запускать второй процесс поверх уже работающего на том же порту не нужно. Не используйте другой origin: сервер проверяет его для браузерных операций.

Проверка готовности для текущего адреса:

```sh
curl --fail http://127.0.0.1:8088/healthz
curl --fail http://127.0.0.1:8088/readyz
```

Для собственной БД скопируйте `.env.example` в новый `.env`, заполните `DATABASE_URL`, `PUBLIC_URL`, `HTTP_ADDR` и уникальный пароль администратора. Шаблонные пароли приложение не принимает. При существующем `.env` редактируйте его, не перезаписывая настройки. Затем:

```sh
make build
./bin/gigaquizz
```

Миграции применяются при старте под блокировкой. Для отдельного шага миграции есть `./bin/gigaquizz -migrate-only`. `DURABILITY_REQUIRED_STANDBYS=0` относится к обычной одиночной dev-БД; включать режим с репликацией без настроенного стенда нельзя. Политика репликации описана в [runbook.md](runbook.md).

Проверки проекта

```sh
make check
make build
```

`make check` включает race detector и vet. Тесты реальных зависимостей включаются явно. Для PostgreSQL, созданной `make dev` через локальный Unix socket:

```sh
TEST_DATABASE_URL="postgres://gigaquizz@/gigaquizz?host=$PWD/.local&port=55432&sslmode=disable" \
  make integration
```

Тесты используют свои отдельные схемы. Для Docker-сценария нужен URL тестовой БД с паролем и TCP-портом; не копируйте socket-URL в такой запуск. Браузерный сценарий создаёт настоящий минутный опрос в локальном приложении:

```sh
npm ci
npx playwright install chromium
E2E_BASE_URL=http://127.0.0.1:8088 npm run test:e2e
```

Для него дополнительно нужны Node.js/npm и браузер. На macOS тест умеет использовать установленный Google Chrome. Пароль берётся из `.env`; не публикуйте этот файл или тестовые данные с ним.

RAM-измерение

```sh
go build -o bin/corebench ./cmd/corebench
python3 scripts/profile_core.py --label core_example -- \
  -rate 1800000 -workers 8 -shards 256 -buffer-size 256 \
  -coalesce 250us -max-lag 100ms -repeat-every 20 -allow-large
```

Это проверка 108 млн новых ключей и 5,4 млн повторов в RAM. Нужны несколько GiB свободной памяти и резерв диска для артефактов; память исчезает после завершения процесса. Kafka для этого режима не требуется. [Измеренные результаты](core-results.md), [все параметры](core-benchmark.md).

Журнал Kafka

Дополнительно потребуются Java 21, Python 3.12+ (либо 3.11.4+), свободные порты 19092–19094 и 19192–19194, несколько GiB RAM и свободный SSD. Стенд загружает зафиксированный Apache Kafka 4.3.1 с проверкой контрольной суммы и создаёт три локальных брокера. Это три процесса на одном компьютере, не три независимые зоны.

```sh
make kafka-up
make kafka-status
make kafka-test
```

Для старого формата журнала:

```sh
python3 scripts/profile_log.py --label legacy_example -- \
  -mode direct -rate 1000 -workers 256 -partitions 8 \
  -batch-size 1000 -linger 20ms -allow-large
```

Для нового пакетного формата и повторной проверки после завершения процесса см. [frame-benchmark.md](frame-benchmark.md). Каждый прогон требует нового label; прежние отчёты не перезаписываются. Нагрузки выполняйте последовательно, отдельно от компиляции и тестов. Большая заявленная частота не равна фактической: проверяйте ACK, пропуски, отказы, неизвестные исходы и полный аудит.

Остановка Kafka без удаления данных:

```sh
python3 scripts/kafka_lab.py stop
```

Если скрипт сообщает, что конкретный принадлежащий стенду процесс не завершился, сначала посмотрите его состояние и логи. Для такого процесса предусмотрен явный `stop-node --node N --hard`; это принудительная остановка, которая потребует восстановления Kafka при следующем старте. Каталоги старых журналов вручную для освобождения места не удаляйте.

Деплой в production

Текущий `make dev` предназначен для локальной разработки. Массовый production-путь ещё требует интеграции владельцев разделов, публикации результатов, защищённых сетевых соединений и испытаний отказа зон. Характеристики узлов, количество, формулы и порядок выхода в production находятся в [production.md](production.md). Покупка указанного числа машин сама по себе не превращает экспериментальные бинарники в готовый production-сервис.
