# Ревью и подготовка к переносу — 14 сентября 2026

Обе ветки подготовлены к запуску одним процессом приложения на более мощном Linux-сервере. Исходники под конкретный CPU или объём RAM менять не нужно: переносится release своей архитектуры, данные и конфигурация. Для postgres-kafka отдельно должны работать PostgreSQL и три Kafka-брокера. Проверка всего сайта на 100M пользователей за минуту остаётся незавершённой; переносимость и пропускная способность — разные проверяемые свойства.

## Найдено и исправлено

| Проблема | Изменение и проверка |
|---|---|
| Go уже прочитал runtime-переменные к моменту загрузки app env, поэтому одного os.Setenv было недостаточно | GOMEMLIMIT/GOGC/GOMAXPROCS из файла явно применяются через runtime API после проверки. Отсутствующий GOMAXPROCS сохраняет автоматическое поведение. Тест проверяет фактические значения, Linux smoke — cgroup CPU |
| Некорректный PUBLIC_URL или занятый HTTP-порт могли обнаруживаться после открытия хранилища | Общая HTTP-валидация выполняется заранее; listener открывается до storage. Тесты подтверждают отказ без создания DATA_DIR или подключения к недоступным тестовым хранилищам |
| Не было команды проверки серверного профиля без запуска приложения | Добавлен -check-config: проверяет конфигурацию и показывает действующие лимиты без подключения к PG/Kafka, открытия listener или создания данных. DSN, пароли и пути в отчёт не входят |
| В files допускался противоречивый предел уникальных ID на партицию | Конфигурация и прямое открытие store отвергают предел партиции выше общего. В PG нормализован тот же default, чтобы отчёт совпадал с реальным запуском |
| PG owner-check мог ошибочно считать отмену ожидающего mutex запроса потерей владельца | После получения mutex повторно проверяются контекст вызывающего и состояние владельца. Ошибка реального SQL-подтверждения по-прежнему закрывает приём; автоматический захват не добавлен |
| PG readiness зависела от длительного пересчёта и могла включиться поздним health-check после начала shutdown | Проверка здоровья выполняется отдельно; shutdown закрывает readiness через общий gate, поздний результат её не включает. Тесты проверяют эти гонки |
| Не было полного серверного профиля и unit в комплекте | Сборщик включает env-профиль, systemd-службу и SERVER-DEPLOYMENT.md в SHA256SUMS. Отсутствие любого обязательного файла делает сборку неуспешной |

Повторное чтение охватило изменённые пути запуска, конфигурацию, отмену owner-check, readiness, сборщик и установку. Новых неустранённых блокирующих ошибок в этом объёме не обнаружено. Вспомогательные интерфейсы readiness оставлены для независимых проверок здоровья и тестирования гонок; новых универсальных слоёв хранилища нет. Проверка не доказывает отсутствия всех ошибок в проекте.

## Запуск на другом сервере

[Инструкция установки и переноса](server-deployment.md) содержит готовые команды, права каталогов и systemd unit. Стартовый кандидат — 64 выделенных vCPU, 128 GiB RAM, локальный NVMe от 1 TB с защитой от потери питания, 25GbE. Это профиль для измерения; число CPU, RAM и сетевой порт не являются доказательством 1,667M голосов/с.

Профиль задаёт 32 партиции, MAX_INFLIGHT=65536, очереди по 8192, GOMEMLIMIT=96GiB. Локально память уменьшена до 2GiB, затем до 3GiB при переносе. На сервере достаточно выбрать бинарник под Linux amd64/arm64 и изменить конфигурацию в пределах его бюджета. Работающему приложению Go/Python/Node не нужны, сайт и QR встроены.

Files переносит весь DATA_DIR после остановки исходного процесса. PG сохраняет ту же БД/схему и те же Kafka topics. Одновременных владельцев нет. Перенос не меняет минуту опроса; новые настройки партиций применяются к будущим опросам. Исторические результаты сравниваются после завершения их проверки в фоне.

## Проверки этой версии

Итоги HTTP-проверки и переноса приведены в [машиночитаемых отчётах](measurements/2026-09-14/server-ready/README.md).

| Измерение за минуту | simple-files | postgres-kafka |
|---|---:|---:|
| План уникальных ID | 60000 | 60000 |
| План POST с повторами | 68571 | 68571 |
| Подтверждено POST | 68571 | 68217 |
| Уникальных голосов в финале | 60000 | 59694 |
| Пропущено генератором попыток | 0 | 294 |
| Journey завершился без POST | 0 | 57 |
| POST отклонён после закрытия | 0 | 3 |
| HTTP GET / ошибки GET | 300000 / 0 | 298661 / 38 |
| Подтверждений, не найденных в журнале | 0 | 0 |
| Подтверждений, оставшихся без сверки | 0 | 0 |

Каждое повторное голосование использовало тот же ID; оригинальная попытка проходила пять GET и POST. Два генератора, приложение и, для PG, все хранилища работали на одном Mac. Все 38 ошибок GET в PG классифицированы как таймауты, ответы с неверным HTTP-статусом не обнаружены. Причина задержек между приложением, генераторами, ОС и брокерами этим прогоном не локализована. PG не принял весь план: 306 уникальных ID отсутствуют в финале. Нулевая потеря подтверждённых записей не означает нулевую потерю желавших проголосовать. Средний клиентский POST RTT составил 52,81ms files и 58,55ms PG; это не измерение занятости POST-слота и не прогноз для нового сервера.

После остановки files перенесены 101 файл, 3526705 байт; SHA256 каждого совпал. Обе ветки запущены из нового каталога с теми же хешами бинарников и GOMEMLIMIT=3GiB вместо 2GiB. Старое разбиение на 32 партиции, время опроса и финальный результат сохранились при новом default на 64 партиции. Независимый reader подтвердил каждый ACK; Kafka reader прочитал полный snapshot всех 32 партиций.


Полные go vet ./... и go test -race -count=1 ./... прошли в обеих ветках. Python: 66 тестов files и 90 PG, включая сборку комплекта. PG suite использовал локальную PostgreSQL с изолированными схемами; управляемые opt-in сценарии отказов Kafka в этом этапе не повторялись. После последней правки остановки files отдельно повторён пакет cmd/gigaquizz с race detector. Вспомогательная правка gofmt в PG filebench меняет только пустую строку.

Review-комплекты собраны для darwin/arm64, linux/arm64, linux/amd64. На Linux arm64 фактически выполнен -check-config обеих веток под ограничением двух CPU и 512MiB RAM: применён GOMEMLIMIT=256MiB из файла, GOMAXPROCS=2 выбран Go. Файловая ветка прошла HTTP-создание опроса, три подтверждённых отправки с одним ID → один итоговый голос, SIGTERM с exit 0, restart, неизменный результат, аннулирование старой admin-сессии и HTTP 410 после закрытия. Контейнер запускался без root, с read-only корнем; данные находились в bind mount с Mac. Это функциональная проверка Linux, а не измерение Linux NVMe/fsync.

Systemd unit прошёл systemd-analyze verify без замечаний на Ubuntu 24.04.4 LTS, systemd 255.4: изолированный staging root содержал исходный unit, реальный Linux-бинарник и базовые unit-файлы VM. Генераторы отключены, служба не устанавливалась и не запускалась под PID1. Это проверка unit, а не выполнение всех его ограничений при работе приложения.

Полный Linux-стенд PG/Kafka не развёрнут: внутри существующей Docker VM оставалось 6,41GiB, ниже установленного для стенда резерва 8GiB. Новые образы не загружались, существующие службы не изменялись. Linux amd64 проверен сборкой; TLS/SASL, внешний балансировщик, отдельный физический сервер и 100M HTTP/min здесь не проверены.

Первый Linux fixture сравнивал historical result сразу после readiness и встретил ожидаемый pending. Исправлен сценарий ожидания финала; production-код для этого не менялся. Во время разработки также исправлены проверки диагностического CPU profile и тестовый New(nil): итоговая suite проходит с ненулевым context и сохранённым контрактом явного профилирования.
