# Нагрузочные и отказные проверки

`cmd/loadtest` — ограниченный генератор POST для одного опроса. Он нужен для воспроизводимых локальных проверок вертикального среза и диагностики ограничений генератора. Его наличие и успешный запуск не подтверждают готовность к 100 млн голосующих за 60 секунд.

## Подготовка локального прогона

1. Запустить приложение и хранилище, выполнить bootstrap администратора и вход по [README](../README.md). Использовать отдельное тестовое окружение и опрос без других голосующих.
2. **До создания опроса** собрать генератор, чтобы компиляция не заняла часть минутного окна:

   ```sh
   go build -o /tmp/gigaquizz-loadtest ./cmd/loadtest
   ```

3. Через защищённый `POST /api/admin/polls` создать опрос. Способ передачи административной cookie описан в README. Пример тела:

   ```json
   {"question":"Локальная проверка","type":"single","options":["A","B"]}
   ```

   Сохранить `id` из ответа. Без `starts_at` опрос начинается сразу и принимает новые голоса одну минуту. Для подготовленного старта можно передать `starts_at` в RFC3339; генератор запускать после начала окна. Пароль и административная cookie генератору не передаются.

4. Подставить UUID и запустить небольшой прогон в пределах открытого окна:

   ```sh
   POLL_ID='UUID-ИЗ-ОТВЕТА-СОЗДАНИЯ'
   /tmp/gigaquizz-loadtest -poll "$POLL_ID" > /tmp/gigaquizz-load-report.json
   ```

По умолчанию планируются **100 логических голосов за 10 секунд**, один вариант с ID 1, 16 работников, очередь 64, тайм-аут попытки 5 секунд. Начальный слот приходится на время запуска, последний — на 9,9 секунды. После расписания выполняются только уже начатая работа и разрешённые повторы; общий срок ограничен окном плюс `-drain-timeout` (по умолчанию ещё 10 секунд).

Проверка дублей на новом опросе:

```sh
/tmp/gigaquizz-loadtest -poll "$POLL_ID" -rate 10 -duration 10s \
  -duplicate-every 2 > /tmp/gigaquizz-duplicates-report.json
```

Каждая вторая позиция исходного расписания, если она дошла до отправки, получает один дополнительный POST после завершения первой попытки, включая завершение тайм-аутом. Токен и выбор остаются прежними. Без пропусков ожидается 100 логических операций и 150 HTTP-попыток. При исправном сервисе и отсутствии посторонних голосов — 100 ответов 201, 50 ответов 200, 100 логических подтверждений и 100 голосов в окончательных результатах. Эти числа являются **ожиданием теста**, а не результатом проведённого измерения.

Новый запуск генерирует новые случайные токены: на прежнем опросе он добавляет новые логические голоса. Для сравнения прогонов нужен новый опрос после закрытия предыдущего. Генератор не хранит токены на диске и не умеет повторить их после своего перезапуска.

После окна приёма дождаться окончательных результатов через защищённую админку/API и сверить их с отчётом. Промежуточный снимок не является окончательным. Для multiple choice один участник может увеличить несколько счётчиков; сумма счётчиков вариантов не равна числу голосов в общем случае. CLI выбирает один вариант и не покрывает все комбинации multiple choice.

## Расписание и ограничения генератора

Расписание открытое: слот `i` назначается на `start + i/rate` по монотонной шкале Go. Скорость поступления слотов не зависит от ответов сервиса. Работники отправляют запросы из ограниченной очереди; переполнение не растягивает расписание. Слоты старше `-max-lag` (100 мс по умолчанию) пропускаются планировщиком или работником. Просроченные слоты удаляются массово, без попытки внезапно наверстать весь пропущенный поток.

Повторы занимают тех же работников. Поэтому медленный сервер, большое число дублей или медленный генератор приводят к явно посчитанным пропускам. `-workers` и `-queue` — ограничения ресурсов, а не обещание заданного RPS. Увеличение `-max-lag` допускает большее отклонение фактической отправки от профиля; для строгого профиля пропуски и задержки генератора должны входить в критерии невалидного прогона.

HTTP-соединения переиспользуются; число соединений на хост ограничено числом работников. Размер читаемого ответа ограничен 64 KiB. Переадресации не выполняются; автоматические повторы POST не включены. Прокси из окружения не используются, чтобы локальный адрес по умолчанию оставался локальным.

`-allow-high-load` требуется для цели вне loopback IP, максимального среднего потока с учётом дополнительных POST выше 1000 попыток/с или общего плана выше 100000 HTTP-попыток. DNS-имена, включая `localhost`, требуют этот флаг; для локального запуска использовать `127.0.0.1` или `[::1]`. Флаг — защита от случайного запуска; он не заменяет согласование плана и бюджета полного испытания. В примерах этой инструкции внешняя нагрузка не запускается.

Дополнительные ограничения параметров: окно не более 24 часов, `-timeout` и `-drain-timeout` не более 5 минут, `-max-lag` не более минуты, число работников до 10000, очередь до 100000. Это ограничения CLI, не рекомендуемые настройки системы. Остановка по SIGINT/SIGTERM отменяет новые отправки, освобождает ресурсы и печатает накопленный JSON; прерванные сетевые операции могут иметь неопределённый исход.

## Как читать JSON

| Поля | Что измеряют |
|---|---|
| `logical_planned` | Полное число слотов исходного расписания |
| `logical_scheduled`, `logical_not_scheduled` | Обработанные планировщиком слоты, включая пропуски, и остаток при досрочной остановке |
| `logical_enqueued`, `logical_dispatched` | Попадания в очередь и логические операции, дошедшие до первичной отправки |
| `logical_skipped`, `skipped_by_reason` | Пропуски из-за задержки планировщика, заполнения очереди, задержки работника, отмены или ошибки получения случайности |
| `http_attempts` | Явные вызовы HTTP-клиента, включая намеренные повторы; это не счётчик пакетов, соединений или записей сервера |
| `http_attempts_started_during_window`, `http_attempts_started_after_window` | Начала HTTP-попыток до и после конца окна генератора |
| `http_attempts_during_window_per_configured_second` | Попытки внутри окна / заданная длительность; при досрочной остановке знаменатель остаётся заданным |
| `http_attempts_per_elapsed_second` | Все попытки / фактическое время исполнения с завершением работы |
| `http_response_headers_received`, `http_responses_fully_read` | Полученные статусы HTTP и полностью прочитанные небольшие ответы |
| `http_statuses` | Все полученные HTTP-статусы; в том числе 201, 200, 409, 410, 425, 503 |
| `accepted_201_responses`, `duplicate_200_responses` | Ответы сервера о новом принятии и о ранее принятом том же выборе |
| `logical_with_acceptance_confirmation` | Логические операции, для которых хотя бы одна попытка получила 201/200; одна операция учитывается один раз |
| `logical_without_confirmation_unknown_outcome` | Нет подтверждения, но был сетевой сбой или 5xx; запись могла сохраниться |
| `logical_without_confirmation_only_other_responses` | Нет подтверждения или неопределённого ответа, получены иные статусы |
| `transport_errors_unknown_outcome`, `unknown_503_responses` | Число неопределённых HTTP-попыток; позднейший успешный повтор может разрешить их исход на уровне логической операции |
| `response_body_errors` | Ошибки чтения/слишком большой ответ; заголовки 201/200 всё равно считаются подтверждением |

Баланс после завершения работы: `logical_planned = logical_scheduled + logical_not_scheduled`; `logical_scheduled = logical_dispatched + logical_skipped`; `logical_dispatched` равно сумме трёх логических исходов. `logical_enqueued` включает и те операции, которые затем были пропущены работником.

409 означает конфликт выбора, 410 — закрытый опрос для нового голоса, 425 — ещё не начавшийся опрос, 503 — неопределённый исход, допускающий проверку/повтор тем же ключом. Отсутствие 201 **не доказывает потерю голоса**: сервер мог сохранить его перед тайм-аутом. Получение 201/200 также само по себе не проверяет сохранность после отказа — необходима последующая сверка с источником данных и окончательными результатами. Код завершения CLI 0 означает, что JSON сформирован; успешность нагрузки определяется содержимым отчёта.

Четыре распределения задержек:

- `initial_dispatch_lag`: от назначенного слота до начала обработки первой отправки.
- `http_attempt_elapsed`: от начала HTTP-вызова до чтения ответа или ошибки.
- `http_attempt_end_to_end_from_logical_schedule`: от исходного слота до завершения каждой попытки; для повтора включает время предыдущей попытки.
- `logical_end_to_end_including_optional_retry`: от исходного слота до завершения логической операции, включая намеренный повтор.

Во всех распределениях есть число наблюдений, среднее, максимум и p50/p95/p99. Процентили — верхние оценки по фиксированным корзинам с шириной примерно 10% выше 1 мкс; это не точные порядковые статистики. Память гистограмм не растёт с числом запросов. Распределения включают успешные и ошибочные завершённые попытки соответствующей группы; пропущенные слоты показаны отдельными счётчиками и не имеют выдуманной задержки. Низкая задержка при множестве быстрых отказов не означает выполнения SLO.

## Проверки корректности и отказов

Локальные тесты генератора:

```sh
go test ./cmd/loadtest
```

Они проверяют отсутствие ожидания свободной очереди, учёт устаревших слотов и отмены, арифметику длинного расписания, границы гистограммы, защиту параметров и разрешение исхода «503 после принятия → 200 на повторе» без двойного логического счёта.

Конкурентные дубли, разные ответы с одним токеном, сохранение перед потерянным подтверждением, гонка закрытия с допущенной операцией и пересчёт после перезапуска проверяются интеграционными тестами приложения/хранилища: команды и требования к тестовой БД — в README. Последовательный `-duplicate-every` не заменяет эти тесты и не воспроизводит конкурентное использование одного ключа.

Для эксперимента с отказом процесса на отдельном локальном окружении: создать новый опрос, начать маленький прогон, остановить процесс приложения, восстановить его и получить окончательные результаты. Сопоставить период остановки, сетевые ошибки, неизвестные исходы и число подтверждённых логических операций. Такой эксперимент проверяет наблюдаемое поведение процесса; потеря зоны, кворума или диска требует другой испытательной среды. Не интерпретировать неизвестные исходы как точно потерянные записи.

## План подтверждения масштаба — до дорогого запуска

Полномасштабный прогон требует отдельно согласованных плана и бюджета. Этот CLI не автоматизирует развёртывание внешних ресурсов и не является распределённым координатором нагрузки.

1. Зафиксировать регион, модель отказов, целевые p95/p99, допустимую долю голосований без подтверждения за минуту, допустимость потери подтверждённых записей, срок окончательных результатов и предел нагрузки. База остаётся **100 млн фактических голосующих / 60 с = 1 666 666,67 логических голосов/с одного опроса**, без повторного применения конверсии.
2. Измерить возможности генераторов, сети и тестируемых компонентов на небольших ступенях. Проверить задержку генератора, пропуски, CPU, память, соединения и независимые серверные счётчики. Число генераторов и экземпляров сервиса определить по измеренной устойчивой производительности при целевой задержке и выбранном запасе, без экстраполяции как доказательства.
3. Подготовить распределённое расписание с уникальными ключами и ровно 100 млн логических операций, включая дробный средний темп. Целочисленный `-rate` данного CLI и несколько независимых запусков сами по себе точный общий объём и синхронизацию не обеспечивают. Проверить разброс старта и монотонные локальные часы; распределённые гистограммы объединять по счётчикам корзин, а не усреднять p99.
4. Отдельно испытать доставку страницы/статики/вопроса через CDN, холодное открытие, TLS-соединения и origin. POST-only прогон исключает основную раздачу страницы и не подтверждает весь путь пользователя.
5. Добавить согласованные всплески, например 50% или 80% за первые 10 секунд с оставшимися голосами за следующие 50 секунд, 0/10/30% дополнительных попыток, массовые конкурентные дубли и тесты отказов на границах сохранения. Перед каждым событием проверить прогрев, квоты и готовность репликации; не включать новые отказы в стоимость молча.
6. Для каждого прогона определить критерии остановки, верхний предел расходов, длительность аренды и порядок освобождения ресурсов после сверки. Посчитать `число × тариф` для запросов, сетевого трафика по каждому участку, записи/репликации/чтения, хранения, генераторов, вычислений, балансировки, прогрева, журналов и метрик. Учитывать платное время подготовки и завершения, а не только минуту входящего потока; актуальные тарифы и квоты выбранного провайдера проверить до согласования.
7. После прогона отдельно сверить запланированные и реально отправленные логические операции, HTTP-попытки, полученные клиентом подтверждения, надёжно принятые сервером уникальные ключи и окончательные результаты. До прогона согласовать метод проверки неопределённых исходов и срок хранения тестовых ключей: текущий CLI их не экспортирует. Проверить отсутствие двойного учёта и потери подтверждённых голосов после выбранных отказов. Сохранить конфигурацию, версии, длительности, счётчики и методику; токены не помещать в логи или метки метрик.

План не содержит придуманных серверных бенчмарков, числа серверов или цен. Успешный локальный вертикальный срез и подтверждение заявленного масштаба имеют разные критерии готовности.
