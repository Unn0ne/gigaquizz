# Упрощение до Go и файлового журнала

Обновление от 10.09.2026. Файловый Store и отдельный минутный стенд реализованы в `internal/filelog` и `cmd/filebench`; [запуск](file-benchmark.md), [измерения](file-results.md). Подключение к HTTP, кабинет на файлах и публикация `result.json` ещё предстоят. Цель прежняя: 100 млн новых голосов за 60 секунд, повторы сверх этого, первый выбор браузерного ID окончательный. Один процесс объединяет HTTP, административный кабинет и пересчёт. PostgreSQL и Kafka можно убрать из варианта с локальным хранением. Сохранность при потере единственного хоста или диска при этом потребует отдельного решения.

Кандидат для ближайшего эксперимента — один Go-процесс и каталог на локальном диске:

```text
data/<poll-id>/
  poll.json       вопрос, варианты и неизменяемое расписание
  votes.wal       последовательный бинарный журнал попыток
  result.json     результат полного пересчёта
```

WAL при необходимости делится на небольшое число сегментов. Общий журнал заменяет миллионы отдельных файлов или обновлений одного JSON-массива. Административные данные читаются заранее и не требуют дисковых обращений на каждый голос.

Путь подтверждения:

```text
HTTP → проверка и допуск → ограниченный пакет → полная запись + sync → ответ
```

Один владелец журнала задаёт порядок записей. В пакете остаются полный 128-битный ID, выбор и серверное время допуска; заголовок содержит версию, длину, количество, последовательность и контрольную сумму. Дедупликацию можно выполнять после закрытия: сохраняем попытки, учитываем первый допустимый ID по порядку журнала. Успешный ответ тогда подтверждает сохранённую попытку, как в текущем Kafka-прототипе. Публичный PostgreSQL API с окончательной квитанцией потребует отдельной адаптации к этому контракту.

Обычный успешный `write` ещё не означает сохранение на носителе и может записать лишь часть буфера. Для Linux кандидат — полная запись и успешный `fsync`/`fdatasync` всей группы перед подтверждением. Каталоги при создании файлов также требуют синхронизации. Режим сохранности необходимо проверить на целевой ОС, файловой системе и устройстве; поведение macOS нельзя автоматически объявлять эквивалентным Linux. [write](https://man7.org/linux/man-pages/man2/write.2.html), [fsync](https://man7.org/linux/man-pages/man2/fsync.2.html).

Расчёт использует условный бюджет 32 B на попытку: существующий codec уже содержит 28 B полезных полей, оставшийся бюджет приблизительно учитывает упаковку. Это бюджет для планирования. Реализованный формат содержит 80 B заголовка WAL, 40 B заголовка на frame до 4096 попыток, по 28 B на попытку и 40 B маркера CLOSED. При полных frames 102 млн попыток занимают около 2,857 GB. MB и GB — десятичные.

| Показатель | 100 млн новых голосов | С условными 20% повторов |
|---|---:|---:|
| Попытки за минуту | 100 млн | 120 млн |
| Попытки/с | 1 666 667 | 2 000 000 |
| Журнал одной копии | 3,20 GB | 3,84 GB |
| Прикладная запись | 53,33 MB/s | 64,00 MB/s |
| Пакет за 10 ms | около 16 667 попыток | 20 000 попыток |
| Размер такого пакета | около 0,533 MB | 0,640 MB |

При пакете 20 тыс. попыток на 2 млн/с полная запись и синхронизация должны в среднем укладываться быстрее 10 ms; 7 ms соответствуют условной загрузке 70%. Следующий буфер накапливается параллельно записи. Это критерий испытания, не измеренная производительность диска. Хвосты задержки sync, ограничение очереди и приём HTTP проверяются отдельно. Синхронизация на каждый отдельный голос не предлагается.

Для сравнения, [RAM-ядро](core-results.md) уже обработало 108 млн новых ключей за минуту с точной сверкой, пик RSS всего процесса около 2,74 GiB. Добавление дискового журнала и HTTP увеличит расходы. [Компактный Kafka-прототип](frame-results.md) на плане 1,7 млн/с подтвердил 70,25 млн из 102 млн; восемь последовательных writers почти непрерывно ждали транзакции. Локальный журнал убирает этот протокол, но вводит ожидание sync; сравнение с ним приведено в [результатах файлового стенда](file-results.md). Удаление PostgreSQL только из хранения настроек не ускоряет Kafka-путь: каждый голос к этой БД уже не обращается.

Обязательные условия корректности файлового варианта:

- Допуск выполняется по серверному времени после получения места в ограниченной очереди. В 60 секунд допуск закрывается; ранее допущенная попытка может быть записана позже. После дописывания очереди сохраняется и синхронизируется `CLOSED` с конечной последовательностью; закрытый опрос не открывается повторно при откате часов.
- Успех и успешный ответ о повторе нельзя возвращать за содержимое только RAM-очереди. Ошибка или неопределённый исход записи прекращают подтверждения затронутых попыток до разрешения состояния.
- После сбоя читаются проверенные полные пакеты. Неполный хвост, возможная порча середины и повреждение уже подтверждённых данных требуют разных решений; произвольно отбросить всё после первой ошибки нельзя.
- Полностью сохранённая попытка, ответ на которую потерялся, может попасть в результат. Повтор до дедлайна использует тот же ID. Итоговый пересчёт не должен удваивать голос.
- В первом эксперименте перезапуск используется для восстановления журнала и результата, без автоматического возобновления приёма. Содержимое потерянной RAM-очереди не считается сохранённым. Восстановление не продлевает минуту голосования; запись с неизвестным исходом может оказаться полностью сохранена, даже если клиент не получил ответ.
- В одном каталоге работает только один владелец записи с блокировкой ОС. Один флаг `O_APPEND` не защищает от запуска второго независимого владельца. Несколько процессов или серверов не должны одновременно дописывать общий файл без подходящего механизма владения.
- Конфигурация публикуется до старта, результат — после полной сверки: временный файл, синхронизация, атомарное переименование на той же файловой системе, синхронизация каталога. [rename](https://man7.org/linux/man-pages/man2/rename.2.html).

Сохранённый исправный диск позволяет восстановить данные после перезапуска процесса. Потеря единственного диска лишает этой копии; отказ единственного сервера прерывает приём. Фоновая копия после ACK не обеспечивает нулевую потерю подтверждений при таком отказе. Если нужна работа после потери узла, остаются репликация до подтверждения, смена владельца и защита от записи прежним владельцем. Удаление Kafka само по себе эти задачи не устраняет; самодельная репликация по двум TCP-соединениям не считается готовой заменой.

Проверка через SIGKILL не доказывает сохранность при обесточивании. Отдельно проверяются выполнение накопителем обещаний sync и риск повреждения ранее записанных байтов при последующей частичной записи в тот же физический блок. Контрольная сумма обнаруживает порчу, но не восстанавливает единственную копию. Подобные предположения о хранилище явно рассматриваются в [описании atomic commit SQLite](https://www.sqlite.org/atomiccommit.html).

Внешний HTTP может быть дороже журнала: при условном запросе 1 KiB поток 2 млн/с даёт 16,384 Gbit/s входящего трафика до дополнительного overhead. Ответы, TLS, соединения и раздача страницы добавляют нагрузку. Поэтому производительность файлового ядра и 100 млн реальных HTTP-запросов — отдельные ступени проверки.

Изолированный файловый стенд выполняет реальную запись и sync на полную минуту, затем точную сверку полных ID и выборов. Сохранённый клиентский ledger позволяет повторить сверку из нового процесса. Отказные проверки Store используют настоящие файлы и управляемые ошибки записи/sync; имитация ENOSPC не заполняет общий диск. Следующая ступень после этих измерений — HTTP с отдельными генераторами и production-пересчёт произвольных браузерных ID; синтетический AES-аудит стенда его не заменяет.

Один сервер — кандидат для измерения, а не обещанная production-конфигурация на 100 млн участников. Масштабирование определяется измеренной производительностью полного пути и согласованной моделью отказов. Ранее предложенные 39 узлов не используются как обоснованный минимум.
