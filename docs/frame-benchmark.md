Пакетный журнал: следующий шаг после CPU-ядра

`votelog.Store.SubmitFrame` сохраняет до 4096 попыток одного раздела в одной записи Kafka. Это настоящий транзакционный журнал: положительный ответ следует успешному commit, читатель использует `read_committed`. Сохраняются RF3/minISR2, fencing producer, неизменяемые параметры опроса и CLOSED. RAM-результат `votecore` не выдаётся за подтверждение сохранности. Новый путь пока является экспериментом и не подключён к публичному сайту.

Формат v2

| Часть | Размер | Содержание |
|---|---:|---|
| Общий заголовок | 80 B/frame | Версия, неизменяемое определение опроса, количество элементов и размер элемента |
| Элемент | 28 B | Полный token 16 B, маска выбора 4 B, время допуска сервера 8 B |
| Kafka key | 0 B | Раздел передаётся явно; при replay проверяется маршрутизация каждого полного token |

Например, при 4096 попытках payload равен `80 + 28×4096 = 114 768 B`, около 28,02 B/попытку вместо старых 96 B key+value. Это размер полезной записи, без протокольного overhead Kafka, индексов и служебных транзакций. Общий заголовок проверяется против первоначального BOOT; malformed frame не допускает частичного применения своей корректной части. V1 продолжает читаться, и один журнал может содержать оба формата.

Квитанция frame содержит partition, offset, count и серверное время допуска. Позиция отдельной попытки — `(partition, offset, index)`, где index начинается с нуля. Старые одиночные записи имеют index=0. Первый встреченный `(offset,index)` полного token определяет окончательный выбор. Квитанция подтверждает попытку, а не уникальность физического человека или немедленный канонический исход.

Приём, очереди и закрытие

`SubmitFrame` проверяет все ID и выборы и копирует входной буфер. Все элементы должны принадлежать одному разделу. Под блокировкой владельца проверяются его состояние, свободные места в ограниченной очереди и календарный дедлайн; всем элементам присваивается один серверный момент допуска. Клиент не задаёт этот timestamp. Запись, допущенная в 59,9s, может завершить commit после 60s; новые попытки после дедлайна не допускаются.

QueuePerPartition ограничивает количество логических голосов, а не количество frames. Дополнительная память ограничена одним активным транзакционным пакетом. Тайм-аут клиента не отменяет уже допущенную запись: исход становится `unknown`. Ошибка runtime-транзакции останавливает writer; он не получает новую epoch автоматически. Явное восстановление сначала разрешает старую транзакцию, проверяет committed prefix и CLOSED. Production-назначения/leases пока не реализованы.

`Seal` перепроверяет серверное время после пробуждений, закрывает gate и ждёт завершения уже допущенных пакетов, затем фиксирует CLOSED тем же последовательным writer. Контрольная запись не помещается в отдельный несвязанный producer. Незакоммиченный frame исключается целиком; frame после CLOSED считается нарушением протокола. Поздний новый POST нельзя превратить в допуск задним числом.

Генератор и сверка

`cmd/framebench` генерирует полные случайно выглядящие 128-битные ID как AES-перестановку уникальных счётчиков. Каждый key имеет исходный момент на равномерном минутном расписании. Запросы группируются по разделам, frame отправляется при заполнении или по ограниченному возрасту. Генератор имеет ограниченные очереди и число ожидающих вызовов; отставание, переполнение, отказ и неизвестный исход остаются в исходном количестве попыток.

`-repeat-every 20` добавляет конфликтующий выбор 2 для каждого двадцатого key, оригинал имеет выбор 1. Повторы увеличивают попытки сверх заданной частоты новых ID. Первый выбор определяется реальным порядком commit/index, а не порядком намерений генератора. Время загрузки страницы, HTTP, TLS и CDN в этом direct-режиме не измеряется.

Для сверки сохранены состояния каждой синтетической попытки и небольшая квитанция на frame: позиция, count, timestamp и SHA-256 упорядоченных пар token/choice. При чтении Kafka каждый полный token обратным AES-преобразованием проверяется как элемент исходного множества; битовое состояние отмечает каждую оригинальную и повторную попытку и обнаруживает лишние копии. Точная дедупликация не заменяется сокращённым хешем. SHA-256 дополнительно связывает порядок и содержимое frame с клиентской квитанцией; все ACK сверяются с конкретными offset/index/count и временем допуска. Итоговый выбор устанавливается заново из журнала.

`votelog.Replay` отдаёт записи потоком до CLOSED каждого раздела. Генератор не строит map на 100 млн Kafka-позиций и не хранит весь набор Go-запросов. Приватные состояния, AES-параметры и квитанции сохраняются с правами 0600 и могут использоваться для read-only повторной проверки после завершения процесса. Клиентский manifest не является заменой Kafka; падение генератора во время нагрузки до записи его наблюдений этой методикой полностью не покрывается.

Пример запуска

```sh
go build -o bin/framebench ./cmd/framebench
make kafka-up

# Сначала небольшой настоящий минутный контроль.
python3 scripts/profile_log.py --benchmark framebench --label frames_smoke -- \
  -rate 1000 -partitions 8 -frame-size 4096 -frame-age 20ms \
  -repeat-every 5 -allow-large

# Сравнение с прежним direct-журналом: 12 млн новых ID за минуту.
python3 scripts/profile_log.py --benchmark framebench --label frames_200k -- \
  -rate 200000 -partitions 8 -workers 64 -queue 128 \
  -frame-size 4096 -frame-age 20ms -max-lag 100ms -allow-large
```

Для большого прогона `-rate 1700000` означает план 102 млн новых ID. Его можно запускать только после проверки диска и успешного небольшого контроля. Верхние пределы: 1,8 млн новых ID/с, 120 млн попыток с повторами, frame≤4096, 1–32 раздела, workers≤256, очередь≤512 frames. Длительность опроса всегда 60 секунд. Контекст клиента≤15s, бюджет Kafka transaction=30s, дополнительное ожидание генератора≤20s. Это разные тайм-ауты; ни один не расширяет календарное окно допуска.

Результат содержит `private_manifest`. Для сохранённого локального файла:

```sh
bin/framebench -audit-only .local/framebench/ИМЯ_ИЗ_ОТЧЕТА.json
```

Эта команда только читает ранее зафиксированный журнал и клиентские наблюдения; writers она не запускает. Старый `logbench -audit-only` ожидает старый ledger без index и не предназначен для квитанций frames. Если исходный журнал уже удалён retention-политикой или CLOSED отсутствует, точная финальная сверка не должна объявляться успешной.

Локальные ограничения

Все Kafka-адреса остаются числовыми loopback; создавать произвольные внешние topics инструмент не разрешает. До нагрузки проверяются прогнозируемый объём RF3, клиентские файлы и резерв свободного диска 8 GiB. Для этой серии предел объёма принадлежащего проекту Kafka-стенда увеличен с 18 до 26 GiB, чтобы сохранить прежние журналы рядом с новым компактным. Резерв 8 GiB не уменьшен; старые данные автоматически для теста не удаляются.

Обёртка `profile_log.py --benchmark framebench` сохраняет команду, SHA-256 бинарника, раз в секунду CPU time/RSS процесса Go и трёх JVM, а также действия отказного теста. Три локальных брокера на общем SSD не проверяют независимые зоны. Стандартный Kafka ACK не равен fsync каждой записи на всех копиях: модель остаётся репликационной. Производительность RAM-ядра и прямого Kafka-пути в отчётах указывается отдельно.
