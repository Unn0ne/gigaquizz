ADR-001. PostgreSQL для первого работающего среза — принято для разработки 10.09.2026.

Применяется к основному PostgreSQL-сервису. После нагрузочных измерений рекомендация массового приёма пересмотрена в ADR-005 ниже; по запросу пользователя реализован отдельный экспериментальный прототип журнала. Публичный API основного сервиса сохраняется.

Нужна проверяемая атомарность сохранения голоса и уникальности. Выбран PostgreSQL 16+ с pgx/v5: одна функция `record_vote` вызывается одним сетевым обращением. В обычной открытой минуте она сразу делает `INSERT ... ON CONFLICT DO NOTHING`; исход существующей записи читается только при конфликте. Отдельной базы отметок дедупликации нет. Таблица голосов имеет 32 hash-раздела по токену, ключ `(poll_id, token)`; число разделов фиксировано для среза, не рассчитано на 100 млн/мин.

Альтернатива — надёжный журнал попыток и дедупликация после закрытия. Он упрощает работу до подтверждения попытки, но добавляет сохранение повторов, восстановление обработчиков и отдельное определение окончательного ответа. Его локальный прототип и измерения описаны в ADR-005; готовность к целевому масштабу ещё не подтверждена. Один PostgreSQL и внутреннее партиционирование не заменяют распределённое хранилище и предварительно выделенную мощность.

Функция `VOLATILE`, уровень записи READ COMMITTED: после ожидания конкурентного INSERT следующий SELECT получает свежий снимок и видит победителя. Это проверено интеграционным тестом с незакоммиченным конкурентом. Основание: [PostgreSQL 16, изоляция](https://www.postgresql.org/docs/16/transaction-iso.html), [снимки функций](https://www.postgresql.org/docs/16/xfunc-volatility.html). Прочитано 10.09.2026.

Наличие foreign key голосов на опрос помогает целостности, но создаёт внутренние блокировки метаданных/MultiXact. Отсутствие горячего счётчика не означает отсутствие всех узких мест. Условная запись, FK, журнал WAL, fsync, репликация и распределение разделов должны измеряться отдельно.

Для испытаний репликации добавлен явный барьер сохранности восстановленных квитанций: локальный commit после отмены ожидания репликации может ещё не иметь нужной удалённой копии. В реплицированном режиме после чтения проверяется покрывающая commit позиция WAL на фиксированном primary и нужном числе физических реплик. Реализация и границы — в [описании сохранности](replication-durability.md); одно включение синхронной реплики без политики клиента не принимается.

ADR-002. ID браузера на опрос — согласовано пользователем, реализовано 10.09.2026.

Случайный 128-битный ID хранится в IndexedDB под ключом опроса. Пересекающиеся readwrite-транзакции предотвращают создание разных используемых ID и разных pending-выборов при первом открытии вкладок. Первый pending сохраняется до сети; квитанция сохраняется только после ответа. Повторное открытие использует прежний ID, а незавершённый запрос — прежний выбор. Генерация ID не требует HTTP. После подтверждения повторное открытие может показать квитанцию локально.

Устройство/профиль/браузер/очистка данных меняют эту эвристику. При отказе браузерного хранения доступна попытка с ID текущей страницы и явным предупреждением. Результаты не объявляются доказательством уникальности физических лиц. IP, User-Agent и fingerprint не сохраняются. Пользователь разрешил хранение ID без заданного предельного срока; автоматической очистки исходных голосов пока нет. Это облегчает пересчёт и требует отдельной политики хранения при эксплуатации.

Основание: [IndexedDB 3.0](https://www.w3.org/TR/IndexedDB/#transaction-scheduling), [Web Cryptography](https://www.w3.org/TR/webcrypto/#Crypto-method-getRandomValues), проверено 10.09.2026. Сквозного ID между опросами нет.

ADR-003. Дедлайн и окончательные результаты основного PostgreSQL-сервиса — реализовано 10.09.2026.

Авторитетная точка допуска — функция БД после получения блокировки и проверки ответа. Её часы сравниваются с `[starts_at, ends_at)`. Допуск в 59,9 с разрешает commit в 60,2 с; после commit клиент получает подтверждение. Блокировка допуска общая для голосов в одном из 64 логических сегментов; чтения/записи одного poll_id не увеличивают общий счётчик.

Финализатор после дедлайна получает исключительные transaction advisory locks всех 64 сегментов в фиксированном порядке. Он ждёт старые записи, считает итоги и фиксирует `finalized_at` и результаты одной транзакцией. Новые запросы после ожидания перепроверяют состояние и не пишут после финализации. Поздняя проверка квитанции берёт исключительную блокировку только своего сегмента, чтобы отсутствие строки не скрывало незавершённый commit. При пересечении дедлайна между предварительным выбором общей блокировки и допуском возвращается неопределённый исход, без upgrade блокировки и риска взаимной блокировки.

Падение процесса/БД до commit может потерять неподтверждённый голос. Потерянный HTTP-ответ после commit восстанавливается по ключу. `synchronous_commit=on` означает ожидание сохранности согласно конфигурации PostgreSQL; локальный запуск не настраивает синхронные реплики. Нулевая потеря при уничтожении узла, зоны или региона не заявляется. Основание по блокировкам: [PostgreSQL explicit locking](https://www.postgresql.org/docs/16/explicit-locking.html), по сохранности: [WAL configuration](https://www.postgresql.org/docs/16/wal-configuration.html).

Результат до финализации — согласованный REPEATABLE READ снимок; после — сохранённый окончательный агрегат. В multiple choice один ряд голосования добавляет одну единицу в общее число и по одной в выбранные варианты. Повторный запуск финализатора не увеличивает счётчики повторно. «Exactly once» для всей сети не заявляется: ограниченная гарантия — одна сохранённая строка и один учёт на `(poll_id, token)` при сохранности БД.

ADR-004. Ограниченный Go-сервис и эксплуатационные пределы — принято для основного PostgreSQL-среза.

HTTP на стандартной библиотеке, один драйвер pgx. Отдельные пулы массового и административного пути, ограниченные обработчики и соединения, фиксированный размер входа. На голосование выделено до 10 секунд; `context.WithoutCancel` сохраняет начатую операцию при отключении клиента, после чего `WithTimeout` ограничивает её. Работа остаётся в обработчике, а не в неограниченной фоновой горутине. Shutdown ждёт обработчики до 20 секунд, прекращает фоновую задачу и закрывает пулы. Ожидание PostgreSQL ограничено `statement_timeout=30s`, `lock_timeout=5s`, `idle_in_transaction_session_timeout=30s`.

Финализация запускается одним циклом, до 20 опросов за проход и до 15 секунд на проход. Это подходит для локального среза; при 100 млн строк сканирование может потребовать существенно больше времени и отдельного ресурса. Подсчёт и чтение результатов сейчас используют тот же физический сервер БД; полноценной изоляции ресурсов хранения пока нет. Частота результатов не входит в критические требования, поэтому UI обновляет их вручную.

Наблюдаемость ограничена счётчиками и редкими сообщениями процесса, без access logs/тел запросов. Счётчики ответов сервера не доказывают получение ответа клиентом; генератор отдельно считает полученные подтверждения. Полные гистограммы серверных задержек, контролируемая диагностика паник, распределённые трассы без данных участников и событийные SLO — следующий эксплуатационный этап.

Открытые решения до подтверждения масштабной архитектуры: география, переживаемые отказы, SLO минутного события, верхняя нагрузка сверх среднего, выбранный провайдер и бюджет; измеренный throughput с отказом, CDN-кеширование описания без ошибки часов, физическое распределение хранилища, синхронная репликация, миграции/роллинг-обновления, политика резервных копий и удаления. Реализация расширяет согласованную схему поэтапно и не подменяет эти проверки локальным запуском.

ADR-005. Пакетный журнал попыток и последующая дедупликация — предложено 10.09.2026, затем реализовано и испытано как изолированный прототип по запросу пользователя.

Требуемые 100 млн фактических голосов за минуту не обосновываются прежними локальными 6000/с и умножением числа PostgreSQL-групп. Реализованы `internal/votelog` и `cmd/logbench`: ограниченный допуск, транзакционные пакеты Kafka от владельцев разделов, CLOSED, явная смена владельца и точная дедупликация при чтении `read_committed`. Результат и manifest формируются в JSON. Целевая схема сохраняет PostgreSQL для административных данных и публикации итогов; эта интеграция и распределённое назначение владельцев ещё не реализованы. Число разделов не равно числу серверов или независимых кластеров.

Экспериментальный `202 recorded` подтверждает сохранённую попытку после commit пакета, тогда как `201` основного сервиса подтверждает окончательный выбор. Kafka ACK также не равен текущему proof физического flush; модель отказа зоны и требования к полному обесточиванию обозначаются отдельно. Основной PostgreSQL API не переключён на этот контракт. Пакетный SQL остаётся сравнительным вариантом при необходимости прежнего окончательного ACK. [Полный пересмотр](architecture-revision.md) содержит арифметику и протокол, [описание стенда](log-benchmark.md) — команды и ограничения, [результаты](log-results.md) — все выполненные профили. Есть успешные и неудачные HTTP-прогоны; direct-профили не измеряют HTTP. Доступность при отказе остаётся проблемой, целевой масштаб и количество production-узлов не подтверждены.
