# Финальный аудит и перенос на отдельный сервер

Продолжение этого этапа: [ревью серверных настроек и проверка переноса](server-readiness-review.md), [установка systemd-службы](server-deployment.md). Ниже сохранены результаты предыдущего аудита.

14 сентября 2026. Проверяются `simple-files` и `postgres-kafka` после `06fcdc2` и `fd107b4`. Цель этого этапа — комплектность приложения и инструментов, отсутствие скрытой зависимости от checkout и корректный отказ при ошибках развёртывания.

## Что требуется на серверах

| Компонент | simple-files | postgres-kafka |
|---|---|---|
| Приложение | Бинарник нужной ОС/архитектуры, приватный env, постоянный локальный диск | Бинарник нужной ОС/архитектуры, приватный env, доступ к двум хранилищам |
| Хранилища | `DATA_DIR` и доступный для записи родитель | PostgreSQL primary и Kafka минимум с тремя брокерами, RF3/minISR2 |
| Страницы, CSS, JS, QR | Уже встроены в Go-бинарник | Уже встроены в Go-бинарник |
| Go, Python, Node.js на app host | Не нужны для работы готового бинарника | Не нужны для работы готового бинарника |
| Публичный HTTPS | Настроенный reverse proxy и верный `PUBLIC_URL` | То же |
| Генератор нагрузки | Отдельный `httpbench`; для host runner — Python 3.8+, `ps`, часы и ресурсы | То же, генератор подключается только по HTTP(S) |

Для проверенного сценария весь код находится в соответствующих ветках: приложение, миграции, UI и генераторы. Для файловой версии достаточно настроенного application server с диском. Kafka-версия не заработает только от замены HTTP-адреса: PostgreSQL/Kafka, сеть, TLS/SASL и права их роли должны быть подготовлены отдельно.

Один сервер здесь — один владелец данных/схемы. Это не гарантия приёма 100 млн участников за минуту: такого полного HTTP-измерения пока нет. Нужен последовательный внешний smoke и нагрузочные ступени на выбранном железе. Генераторы, обратный прокси, сеть, диск и режим отказоустойчивости также входят в проверку.

## Замечания и исправления

| Находка ревью | Что сделано |
|---|---|
| Ручная сборка могла продолжиться после ошибки и не включала конфигурацию/инструкцию | `build_release.py` собирает полный комплект, отказывает на грязном дереве по умолчанию, проверяет исходники до/после сборки, сохраняет SHA-256 и отмечает неполный результат при ошибке |
| Явно указанный отсутствующий `-env` молча игнорировался | Явный путь обязателен; отсутствие неявного default `.env` по-прежнему допускается для env-only. Приоритет окружения и symlink-secret сохранены; FIFO не блокирует чтение |
| Kafka могла быть недоступна при положительной готовности пустой/finalized схемы | Адреса проверяются до PG; startup/readiness выполняют ограниченный broker-only Metadata probe через тот же TLS/SASL механизм. Голосование не вызывает этот probe |
| Runner удерживал родительские stdout/stderr всех завершённых helpers | Родительские дескрипторы закрываются после `Popen`, ребёнок сохраняет свои копии; атомарная регистрация и обработка сигналов сохранены |
| `go:embed static/*` мог встроить случайный ignored `.env`, не попавший в fingerprint сборщика | Бинарник включает явный список публичных ресурсов; builder отвергает ignored файлы внутри `cmd/internal` до и после сборки, не читая их содержимое |
| Типичный `StateDirectory` мог не дать прав на staging рядом с `DATA_DIR` | Инструкция использует `/var/lib/gigaquizz/data` внутри принадлежащего сервису родителя |
| Требование постоянной PG-сессии не было достаточно явно описано | Указано прямое соединение или session pooling; transaction/statement pooling несовместимы с ownership lock |

Аудиторские методы файлового хранилища и интерфейс Kafka writer имеют реальные вызовы и тесты отказов. Оснований удалять их как неиспользуемые не найдено. Старый `postgres.Store` остаётся частью сравнительных benchmark-команд; рабочее Kafka-приложение использует `kafkapoll`.

## Проверки

Обе сборки перенесены за пределы checkout и запущены из пустых рабочих каталогов с минимальным окружением. Приложения получили настройки только через явно указанный env. Два отдельных runner использовали непересекающиеся диапазоны одного опроса, а родительские процессы runner работали с лимитом всего 16 открытых дескрипторов.

Стенд — один Mac M1 Pro, 10 логических CPU, 32 GiB RAM, Go 1.26.1. HTTP/1.1 без TLS шёл на адрес физического сетевого интерфейса того же Mac. Это проверка переносимости и корректности; отдельной физической машины здесь нет. На каждой ветке — ровно 60 секунд, 60 000 новых ID, один повтор на каждые семь ID и пять GET перед первоначальным POST. JavaScript генератор не исполняет.

Все **137 140 подтверждённых попыток** сопоставлены с полным журналом и сохранённым итогом. Первый ответ каждого ID учтён один раз; лишних записей и расхождений нет. Две попытки Kafka-ветки пришли после закрытия и не были подтверждены. После штатного перезапуска итоги совпали, административная сессия потребовала нового входа, голосование в закрытом опросе вернуло 410.

Дополнительно прошли:

- `go vet ./...` и `go test -race -count=1 ./...` в обеих ветках. PG suite использовал настоящий PostgreSQL с изолированными тестовыми схемами.
- Все Python-тесты: **64/64** в files и **88/88** в PG/Kafka.
- Проверка отсутствующего явного `-env`: оба бинарника завершаются до создания хранилища. Отдельный запуск с недоступной Kafka завершается без создания PG-схемы.
- Сборка с временным ignored `.env` рядом со статикой: приватный файл не попал в embed. Реальный Git-fixture также подтвердил отказ release builder при таком файле. В HTTP-проверке приватные пути возвращают 404, публичные страницы и ресурсы QR доступны, admin API требует входа.
- Сборка полного комплекта для Linux amd64/arm64 и macOS arm64, проверка его файлов по SHA-256. Исполнены только macOS-бинарники; Linux требует smoke на целевой машине.

После фиксации кода выполнена повторная сборка без `--allow-dirty` из чистых коммитов `8ad0cc9` и `ab31aed`. Все 12 бинарников приложения и генератора побайтово совпали с проверочными комплектами; runner, пример env и встроенная инструкция также совпали. [Подтверждение чистой сборки](measurements/2026-09-14/final-audit/clean-rebuild.json) фиксирует полные commit ID и контрольные суммы. Последующие коммиты этого аудита добавляют только документацию и результаты проверки.

Первый общий PG-прогон выявил ошибку нового теста: тот ожидал проверку пароля, не задав обязательный DATABASE_URL. Исправлен тестовый env, полный suite повторён успешно. Проверка offline Kafka сначала ожидала внутренний текст ошибки вместо публичного; её исправили, сохранив проверку кода выхода и отсутствия схемы. Предварительные попытки стенда с symlink-путём и недоступным VPN-адресом не дошли до голосования. История этих проверок сохранена в [агрегатах и происхождении результатов](measurements/2026-09-14/final-audit/README.md).

Проведено ревью до изменений и повторное независимое чтение после них. Конкретных нерешённых блокеров в проверенном объёме не осталось. Опциональные Kafka fault suites и браузерный JS suite на этом этапе не повторялись; содержимое UI не менялось. Ни этот smoke, ни успешная кросс-сборка не подтверждают 1,7 млн HTTP POST/с, работу с production TLS/SASL или устойчивость к потере физического хоста.

## Запуск

[Сборка комплекта и команды для отдельного сервера](external-http.md). Builder выдаёт `RUNNING.md`, `env.example`, `gigaquizz`, `httpbench`, host runner и контрольные суммы. Linux-бинарники собираются без CGO для amd64/arm64. Для проверки локального комплекта можно явно добавить `--target darwin/arm64`.

Оператор задаёт адрес listener, доступный участникам origin, пароль, физические абсолютные пути данных без symlink, пути сертификатов и настройки внешних хранилищ. Нельзя автоматически считать адрес интерфейса VPN подходящим адресом приложения: доступность выбранного IP проверяется с генераторов. У приложения нет встроенного HTTPS listener, автоматического резервирования диска или переключения на другой application host. Эти свойства не возникают от переноса готового бинарника.
