# Теоретический расчёт железа для двух веток

17 сентября 2026. Исходники: simple-files `bdbdfce`, postgres-kafka `8614108`. Это расчёт и чувствительность к допущениям, не установленный минимум и не подтверждение production throughput. [Числа в JSON](hardware-sizing.json). Код и серверные профили этим расчётом не изменяются.

## Условия и граница расчёта

Один опрос, 100000000 уникальных ID за 60 секунд, равномерный поток, ответы только выбором. Базовая частота — **1666667 голосов/с**. Для бюджета берём явно условные 20% дополнительных попыток: **120000000 POST, 2000000 POST/с**. Обе ветки записывают повторы в журнал, дедупликация выполняется при итоговом подсчёте. В бюджет CPU/сети добавлен резерв: средняя загрузка не выше 70%. Это не резерв на потерю целого сервера.

Ниже приложение принимает POST через внешний CDN/edge/reverse proxy с ограниченным пулом повторно используемых соединений. Публичные GET кэшируются, клиентские TLS и соединения обслуживаются этим внешним контуром. Его стоимость и вычислительные ресурсы **не входят** в таблицу серверов приложения; требования к его потоку приведены отдельно. Без этого допущения приведённые RAM/сеть недостаточны.

## 1. Сколько данных действительно сохраняется

Из текущего кода: ID 16 B + выбор 4 B + время допуска 8 B = **28 B на попытку**. Files добавляет 40 B на frame; Kafka — 80 B на прикладной frame. Форматы: files `internal/filelog/codec.go`, Kafka `internal/votelog/frame.go`. Это packed HTTP-путь; старый Kafka singleton имеет отдельный формат 80 B value + 16 B key.

При P32, linger 2ms и лёгком commit номинально выходит 16000 групп/с, то есть 960000 за минуту. Среднее заполнение — 104 голоса без повторов или 125 с 20% повторов. Время commit, заполнение очереди и планировщик меняют эту частоту. Формулы:

- Files: `28×A + 40×F + P×(80+40)`.
- Kafka values: `28×A + 80×F`, затем три копии при RF3. Нативные Kafka headers/control/indexes сюда не входят.
- A — попытки, F — реальные групповые frames. Таблица предполагает сгруппированные записи, а не singleton на каждый POST.

| На один опрос | Без повторов | С 20% повторов |
|---|---:|---:|
| Files WAL | 2,838 GB | 3,398 GB |
| Files средняя запись | 47,31 MB/s | 56,64 MB/s |
| Kafka, прикладные values одной копии | 2,877 GB | 3,437 GB |
| Kafka, три копии values | 8,630 GB | 10,310 GB |
| Kafka, полезная запись на каждый из трёх брокеров | 47,95 MB/s | 57,28 MB/s |

GB/MB здесь десятичные, GiB — двоичные. В Kafka каждый из трёх брокеров при RF3 хранит одну полную копию всех данных опроса, часть как leader, часть как follower. Делить суммарные три копии ещё раз на три и получать треть исходного журнала на брокер было бы ошибкой.

Практический условный бюджет Kafka — **15–25 GB на событие суммарно по трём брокерам**, отдельно внутренние темы, индексы, свободное место и история. Это запас для планирования, не измеренная верхняя граница. Log preallocation и index size зависят от настройки брокера: приложение задаёт segment.bytes=64MiB, но не переопределяет все параметры индексов. При preallocate=true только по одному активному 64MiB segment для P32/RF3 соответствует 6GiB логического пространства. Физические блоки, длина файла, mmap и RSS — разные величины. [Kafka topic configs](https://kafka.apache.org/43/configuration/topic-configs/).

**1 TB для одного опроса из этих объёмов не следует.** Для files 100GB свободного data volume покрывает, например, десять таких журналов (~34GB), вторую копию (~34GB) и остаток под служебные данные; системный раздел учитывается отдельно. Для Kafka можно начать планирование со 100–200GB свободного data volume на брокер при ограниченной истории, затем уточнить фактические внутренние темы/индексы. Это ёмкость, не обещание скорости диска. Текущий Kafka app ставит retention.ms=-1 и retention.bytes=-1; files также не удаляет историю сам. Бесконечное хранение требует роста диска или отдельной согласованной политики архивирования.

## 2. Нужна скорость подтверждения, а не только MB/s

Files делает write→fsync→ACK. На Linux это File.Sync, на Mac — F_FULLFSYNC; результаты разных ОС нельзя приравнивать. Приближённо для неполного batch: `cycle = linger + fsync`, `groups/s = P / cycle`.

| Условный fsync | Групп/с при P32 | Попыток в группе при 2M/с |
|---|---:|---:|
| ≈0 ms | 16000 | 125 |
| 1 ms | 10667 | 188 |
| 5 ms | 4571 | 438 |

Encoding, уведомления и планировщик здесь исключены. Max batch4096 не означает, что groups/s=2M/4096: обычно раньше срабатывает linger. Требуется NVMe с предсказуемой устойчивой записью и подтверждением; паспортные последовательные GB/s этого не доказывают. Файловый параллелизм P32 не создаёт 32 физических диска.

В Kafka один producer на partition последовательно выполняет ProduceSync и EndTransaction. Для текущих P32/B1024 необходимое условие даже при полностью заполненных batches:

`Tcycle ≤ P×B/R = 32×1024/2000000 = 16,384 ms`.

Если полный цикл занимает 20ms, потолок при полном batch — 1,6384M попыток/с, ниже даже частоты без повторов. Увеличение CPU приложения само по себе не устраняет этот потолок. Можно менять P/B/linger через конфигурацию будущего опроса, но это меняет число клиентов, частоту транзакций и задержку; требуется измерение.

Общий MAX_INFLIGHT=65536 требует средней занятости POST-слота менее **32,768ms** при 2M/с, ещё без запаса. Это время обработчика, не p99 и не весь RTT клиента. Очередь не компенсирует нехватку устойчивой пропускной способности.

Kafka transaction commit не означает fsync всех трёх дисков. Его гарантия основана на репликации; совпадение MB/s с files не означает совпадения поведения при общем отключении питания. [Kafka replication and persistence](https://kafka.apache.org/43/design/design/).

## 3. RAM: плановый бюджет приложения — 32 GiB

В обеих ветках финализация идёт **последовательно по партициям**: files `internal/filestore/group.go`, PG `internal/kafkapoll/finalization.go`. При равномерном распределении 100M/P32 это 3,125M ID на один map, сырые ключи — 50MB. Go map имеет накладные расходы; старые объекты живут до GC. Для configured bound 8M/partition выделяем условный бюджет **0,5–1GiB на пересчёт**, а не 100M×размер объекта одновременно. Это бюджет, не замер пикового heap.

Сами pending storage objects при 65536 активных HTTP-обработчиках оцениваются примерно в 19MB files и 17MB Kafka, до HTTP/context/goroutine/клиентских буферов/GC. Большие MAX_UNIQUE и MAX_INFLIGHT не означают предварительного выделения памяти на 100M записей.

Условная раскладка памяти одного app host:

| Статья | Бюджет |
|---|---:|
| До 65536 активных обработчиков при 32–64KiB дополнительного состояния | 2–4GiB |
| До 200000 pooled origin connections при 16–32KiB на соединение | 3–6GiB |
| Финализация и storage buffers | около 1GiB |
| Runtime, GC, ОС, прочее и запас | 4–8GiB |
| Page cache / дополнительный резерв, особенно files | 4–8GiB |
| Плановый размер машины после округления | **32GiB** |

Стоимость обработчика и соединения — **допущения**, а не измеренные константы. Статьи консервативно резервируются отдельно; фактический RSS/сокеты и peak live heap нужно измерять. 16GiB может оказаться достаточно при меньшем пуле и памяти на запрос, но это не установленный минимум. 128GiB не обоснованы объёмом одного опроса.

Kafka broker для одного события: условно 4GiB JVM heap + 6GiB page cache + 6GiB native/OS/запас = **16GiB на брокер**. Долгая история, много partitions/topics, параллельный recovery и эксплуатационные процессы могут потребовать больше. Controller/PG при совмещении получают отдельную долю общего RAM, а не ту же память повторно.

На 32GiB app нельзя оставлять прежний GOMEMLIMIT=96GiB: начальный override порядка 20GiB оставляет память ОС/сокетам/кэшу, затем уточняется по измерениям. GOMEMLIMIT мягкий и не ограничивает весь RSS/память ОС. [Go memory limit](https://go.dev/doc/gc-guide#Memory_limit).

## 4. CPU: формула и калибровка вместо выдуманного RPS на ядро

`CPU cores = attempts/s × CPU seconds/attempt ÷ utilization`.

Это CPU-время, а не elapsed latency ожидания диска. При R=2M и использовании70%:

| CPU на попытку | Расчётная мощность |
|---|---:|
| 10µs | 29 ядер |
| 20µs | 58 ядер |
| 40µs | 115 ядер |
| 60µs | 172 ядра |

64 ядра подходят этому CPU-бюджету только при стоимости не выше **22,4µs/попытку**. Это необходимое условие для мощности CPU, не гарантия пропускной способности: остаются locks, runtime, storage, сеть.

Есть историческая калибровка реального HTTP от 13 сентября:

| Ветка / профиль | App CPU | ACK/с | Грубое CPU/ACK | Условная мощность при 2M/с и70% |
|---|---:|---:|---:|---:|
| Files P8, 4096 workers суммарно | 3,64 ядра | 88655 | 41,07µs | 117,3 ядра |
| PG P16, план50k, два генератора | 1,93 ядра | 45476 | 42,49µs | 121,4 ядра |
| PG P16, план20k | 1,21 ядра | 20000 | 60,34µs | 172,4 ядра |

Источники: [files](measurements/2026-09-13/review-scale/r13_files_post_100000_p8_w2048_g2.json), [PG 50k](measurements/2026-09-13/review-scale/r13_kafka_post_50000_p16_g2.json), [PG 20k](measurements/2026-09-13/review-scale/r13_kafka_post_20000_p16.json). CPU sampled interval около 59s делится здесь на ACK / 60s; это приблизительная калибровка, не точный профиль затрат каждого запроса. Отказы и фон также потребляют CPU.

Это исторический общий Mac, не Linux сервер, без браузерного TLS и cold GET. **117 или172 таких CPU-эквивалента нельзя объявить117/172 vCPU любого облака или гарантией линейного масштабирования одного процесса.** Архитектура CPU, SMT, частоты, kernel, fsync, batch и конкуренция меняют коэффициент. Однако текущие измерения не позволяют обосновать64 ядра как достаточный минимум. При сохранении этого CPU/attempt масштаб бюджета — files около 128 эквивалентных ядер; PG app около 128–192. При снижении стоимости до 20µs обеим веткам на app достаточно CPU-бюджета около 64 таких ядер.

Kafka CPU нужно считать отдельно. Малые групповые записи оплачивают transaction coordinator/markers/репликацию на каждую транзакцию. В историческом PG 50k суммарно три Kafka JVM потребляли 2,10 CPU при ≈353tx/s: грубый коэффициент≈6ms CPU кластера/tx, включая общий фон. Реальная модель — `background + a×tx/s + b×bytes/s`; эти коэффициенты отдельно не установлены.

Чувствительность **только при условном сохранении 6ms/tx**, до отдельной поправки на изменившийся bytes/s:

| Среднее попыток/tx | tx/s при 2M | Ядер на кластер при 70% | На брокер при балансе |
|---|---:|---:|---:|
| 128 | 15625 | 134 | 44,6 |
| 512 | 3906 | 33,5 | 11,2 |
| 1024 | 1953 | 16,7 | 5,6 |

Поэтому 3×8–16 broker CPU могут оказаться достаточными только при удачном batching и latency; это не вывод из 56MB/s. При слабом заполнении условный бюджет поднимается к 3×48 CPU. Больший max batch не доказывает фактическую наполненность. Без калибровки txn+bytes на целевой платформе точного CPU минимума брокеров нет.

## 5. Сеть и входной контур

Если принять **1KiB на POST в каждом направлении вместе с транспортными расходами** как допущение, при 2M/с получается 16,384Gbit/s ingress и столько же egress. При70% полезной загрузки нужен line rate≥23,41Gbit/s: **25GbE условно подходит по байтам**. Если реальный wire size512B, это 8,192Gbit/s; при 2KiB — 32,768Gbit/s и 25GbE уже мало. Для PG/Kafka на общем NIC добавляется примерно 0,458Gbit/s producer egress: суммарно 16,842Gbit/s, или 24,06Gbit/s line rate при 70%, ещё без Kafka protocol/control. 25GbE остаётся условным вариантом с небольшим остатком бюджета. PPS, TLS handshakes, packet loss и возможности сетевого стека эта формула не проверяет.

Внутренняя Kafka-сеть намного меньше: около 57,3MB/s producer→leaders,114,6MB/s на две дополнительные копии; приблизительно 57,3MB/s входящего payload на брокер, без протокола/контроля/повторного чтения. **10GbE на брокер имеет большой запас по объёму**; latency и транзакционные расходы проверяются отдельно. PG metadata не требует сравнимого канала.

Полный сайт без кэша — другой масштаб. В фактическом [HTTP-прогоне 14 сентября](measurements/2026-09-14/server-ready/simple-files.json) пять GET на участника отдавали в среднем 16465B gzip body. Для 100M за60s это **219,53Gbit/s только тел GET**, до заголовков, POST и TLS; всего с20% дополнительных POST — 10,33M HTTP-запросов/с. Все эти GET нельзя молча включить в 25GbE app host.

При одном новом клиентском соединении на человека и удержании 30s было бы около 50M одновременно открытых соединений. В коде IdleTimeout=30s; MAX_INFLIGHT ограничивает только активные voting handlers. Это сценарий, а не измеренное поведение браузеров. Один клиентский keep-alive socket на каждого из 100M участников нельзя заменить оценкой 65536 активных POST. [Go HTTP IdleTimeout](https://pkg.go.dev/net/http#Server).

Внешний контур должен принять исходный поток, кэшировать публичные GET, обслужить TLS и переиспользовать ограниченный пул origin-соединений. Если это собственные proxy-серверы, их число рассчитывается по измеренным HTTP RPS/TLS CPS/соединениям на узел с запасом и выбранным резервированием; доказанной цифры для них здесь нет. Если страница заранее открыта, статика переносится на время подготовки, но поток voting POST сохраняется.

## 6. Сводка для каждой ветки

Это условный инженерный бюджет для приложения и хранилищ, **не заказ оборудования и не доказанный минимум**. CPU-диапазоны требуют калибровки на выбранной модели процессора.

| Компонент | Количество процессов/ролей | RAM-бюджет | Свободный data volume | Сеть | CPU по приведённой модели |
|---|---:|---:|---:|---:|---|
| simple-files app+журнал | 1 | 32GiB | от 100GB NVMe для ограниченной истории | 25GbE | около 128 эквивалентных ядер при сохранении 41µs; около 64 при 20µs |
| PG/Kafka app | 1 | 32GiB | небольшой системный/служебный диск; голоса в Kafka | 25GbE | около 128–192 эквивалентных ядер при 42–60µs; около 64 при 20µs |
| Kafka broker | 3 | по 16GiB | по 100–200GB NVMe с проверкой retention/internal topics | по 10GbE | сценарии около 6–45 эквивалентных ядер/брокер, практический бюджет 16–48 зависит отbatch |
| PostgreSQL metadata | 1 primary | 4–8GiB | 20–40GB SSD как небольшой служебный volume, история/WAL отдельно | обычная внутренняя сеть | 2–4CPU как стартовый бюджет, не результат деления 100M запросов |
| Отдельные KRaft controllers, если роли разнесены | 3 | начально по 8GiB | отдельный небольшой SSD, например 20GB | внутренняя сеть | начально по 2CPU; уточнить для фактической topology |

PostgreSQL не получает 100M INSERT: вопросы, итог, checkpoints 32 партиций, небольшой admin-поток и heartbeat; Vote не делает SQL. Малый PG budget выбран для metadata-службы и не является математическим минимумом. Потеря его owner-сессии всё ещё останавливает app.

Число ролей не равно числу физических серверов. Files помещается на один host и не переживает его потерю. Для компактного PG/Kafka стенда можно использовать 1 app host с PG и 3 Kafka hosts сcombined controllers — 4 hosts; это совмещение ресурсов и не полноценная HA-схема. Apache не рекомендует combined broker/controller для критичных развёртываний. Полное разнесение 1 app + 3 brokers + 3 controllers + 1 PG даёт 8 ролей/узлов, а не потребность в восьми мощных серверах из-за RPS. Резервирование app/PG — отдельная архитектурная работа; текущий код не масштабируется добавлением второго владельца той же схемы. [Kafka KRaft](https://kafka.apache.org/43/operations/kraft/).

При совмещении app и PG их бюджеты складываются: 32GiB приложения плюс 4–8GiB для PG, затем общий запас хоста; при стандартных размерах машины это может означать 48/64GiB. Controller также получает свою долю памяти/CPU. Для отдельных controllers 8GiB — округлённый начальный бюджет с учётом ориентира Apache 5GB для типичной metadata-установки, не доказанный минимум именно нашего кластера.

Реплики Kafka на трёх физических hosts защищают журнал от некоторых отказов отдельных hosts, но не заменяют failover app/PG. 30% CPU-запаса также не доказывают сохранение RPS при выпадении одного брокера. Если эти инфраструктурные службы уже есть, нужны выделенная доля их ресурсов и проверка, а не обязательная покупка новых отдельных машин.

**Что изменилось относительно предыдущей оценки:** ёмкость диска и RAM можно обосновать значительно ниже 1TB/128GiB на app. По CPU столь же уверенно уменьшить прежние 64vCPU нельзя: существующие HTTP-измерения скорее требуют оптимизации или большего CPU-бюджета при сохранении текущей стоимости запроса. Главная проверка будущего сервера — CPU/attempt, fsync/transaction latency, фактическое заполнение batch, origin connection count и полный учёт исходов на2M попыток/с.
