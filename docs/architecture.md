# Архитектура ветки PostgreSQL + Kafka

Актуальная реализация и границы гарантий описаны в [postgres-kafka.md](postgres-kafka.md). HTTP-сайт использует `internal/kafkapoll`: PostgreSQL хранит описания, состояние подготовки и финальные агрегаты; Kafka хранит попытки. SQL в пути Vote отсутствует.

`202 recorded` выдаётся после подтверждённой транзакции Kafka. Writer объединяет соседние одиночные HTTP-попытки в v2 frames, сохраняя время допуска и индекс каждой записи; отдельная непарная попытка остаётся v1. После CLOSED полный пересчёт оставляет первый записанный выбор каждого полного браузерного ID; только затем итог атомарно публикуется в PostgreSQL. До этого `pending: true` означает ожидание результата.

Один контроллер владеет схемой через PostgreSQL advisory lock. Перезапуск сохраняет исходное минутное окно и восстанавливает прежние Kafka producer epochs с fencing. Это не автоматическое HA и не доказательство 1,7 млн HTTP-запросов/с.

[Расчёт полного HTTP-пути](http-capacity.md), [измерения до и после пакетной записи](http-results.md), [точная сверка ACK](http-benchmark.md).

Финализация теперь считает по одной партиции с полными ID, сохраняет проверяемый checkpoint в PostgreSQL и публикует общий результат только после всех CLOSED. HTTP-ветка продолжает иметь одного владельца схемы. Низкоуровневый `votelog.Config.OwnedPartitions` позволяет отдельно проверять передачу партиций между producer, но не включает автоматическое распределение готового приложения. [Ревью и границы готовности](review-scale.md).

Если writer терминально остановился, после дедлайна финализатор дренирует здоровые разделы, закрывает прежних producers, повторно проверяет PG-владение и восстанавливает тот же журнал через fencing. Приём не открывается заново, unknown-попытки не пересылаются. Реальный отказ producer проверен без перезапуска приложения; детали — в [отчёте ревью](review-scale.md).
