# Локальный Kafka-стенд

`scripts/kafka_lab.py` запускает три нативных процесса Apache Kafka **4.3.1** с совмещёнными ролями broker/controller. Это изолированный стенд для нагрузочных и отказных экспериментов новой архитектуры. Все три процесса используют один компьютер и диск; результат не подтверждает производительность распределённого production-кластера или переживание отказа зоны.

Версия и архив проверены 10 сентября 2026 по [официальному каталогу Apache](https://downloads.apache.org/kafka/4.3.1/). Контроллер проверяет архив по опубликованному SHA512 и закреплённому в коде значению; исходный checksum и проверка остаются в `.local/kafka-lab/downloads/verification.json`. Для текущего запуска найден установленный Homebrew OpenJDK 21.0.10; глобальная установка не выполнялась. На другом компьютере можно задать `GIGAQUIZZ_KAFKA_JAVA_HOME` на существующий JDK 21+.

Из корня репозитория:

```sh
python3 scripts/kafka_lab.py up
python3 scripts/kafka_lab.py status
python3 scripts/kafka_lab.py stop-node --node 1 --hard
python3 scripts/kafka_lab.py start-node --node 1
python3 scripts/kafka_lab.py stop
```

`up` сохраняет уже существующие данные. Остановка без `--hard` посылает SIGTERM; `--hard` — SIGKILL, чтобы проверить падение процесса. При остановке всего combined-кластера последний узел может ожидать уже недоступный controller quorum; после 30 секунд контроллер сообщает timeout, дальнейшая принудительная остановка выполняется отдельной командой `stop --hard`. Сигнал посылается только PID с совпадающими временем запуска, именем Kafka и путём конфигурации этого стенда. Контроллер отказывается занимать уже используемые порты. Он не удаляет данные и не взаимодействует с PostgreSQL или `.env` приложения.

Bootstrap servers: `127.0.0.1:19092,127.0.0.1:19093,127.0.0.1:19094`. Controller listeners: `127.0.0.1:19192–19194`. Все listeners привязаны к loopback; здесь PLAINTEXT, без внешнего доступа. Точные PID, JVM, cluster ID и директории находятся в `.local/kafka-lab/metadata.json`. Полные конфигурации находятся в `node{1,2,3}/server.properties`.

Параметры стенда:

| Параметр | Значение |
|---|---|
| Репликация по умолчанию | 3 |
| `min.insync.replicas` | 2 |
| `unclean.leader.election.enable` | false |
| ELR | Явно выключен: `eligible.leader.replicas.version=0` при форматировании |
| Heap каждого брокера | `-Xms512m -Xmx768m` |
| Offset/transaction state topics | RF3; transaction minISR2; обычный minISR2 применяется к offsets |
| Сегмент сырых записей | 64 MiB |
| Retention сырых записей | 24 часа, delete, без compaction |
| Дополнительный предел retention | 1 GiB на раздел по умолчанию |
| Предварительное выделение файлов | Выключено |
| Логи диагностики | WARN; до четырёх файлов по 16 MB на процесс; GC — до четырёх файлов по 16 MB |
| Дисковый guard перед запуском | Не менее 8 GiB свободно, не более 26 GiB выделено стенду |

Ограничение retention применяется к каждому разделу, а не ко всему кластеру. Дисковый guard проверяется при запуске; это не квота файловой системы и не непрерывный watchdog. Генератор обязан ограничивать число записей и проверять свободное место между прогонами. Kafka CLI и launcher также создают небольшие служебные логи; пользовательские записи контроллер не выводит.

`ready=true` означает, что все три принадлежащих стенду процесса живы, а выделенный контрольный topic `gigaquizz_lab_health` имеет ISR `[1,2,3]`. Это не заменяет проверку ISR и конфигураций каждого нагрузочного topic. Проверки readiness запускают Java CLI и заметно расходуют CPU; их следует выполнять между замерами, а не постоянно во время теста.

Producer должен явно использовать `acks=all`, idempotence и ограниченные очереди. Успешный Kafka ACK в этом стенде подтверждает репликацию по правилам Kafka; индивидуальный физический `fsync` каждой подтверждённой записи здесь не обеспечивается. Падение одного процесса и одновременное отключение питания общего компьютера — разные отказные сценарии. [Правила minISR](https://kafka.apache.org/43/configuration/broker-configs/#min.insync.replicas), [ELR](https://kafka.apache.org/43/operations/eligible-leader-replicas/), [хранение и fsync](https://kafka.apache.org/43/operations/hardware-and-os/).

Проверка запуска 10 сентября 2026: все три listener доступны, health topic RF3/minISR2 с ISR `[1,2,3]`; `kafka-features.sh describe` подтвердил ELR finalized level 0. Выполнены SIGKILL одного узла с повторным запуском и полный перезапуск стенда. Итоговый статус сохранён в `.local/kafka-lab/startup-verification.json`, признаки feature level — в `.local/kafka-lab/features-initial.txt`. Это smoke-проверка управления процессами; проверку сохранности подтверждённых голосов выполняет отдельный нагрузочный/отказный сценарий приложения.
