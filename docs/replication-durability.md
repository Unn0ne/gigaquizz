Проверка сохранности при физической репликации, 10.09.2026.

`postgres.NewWithOptions` добавляет явный режим подтверждения на primary и заданном числе именованных физических standby. Нулевые параметры сохраняют режим одной локальной БД. Синхронная конфигурация сервера без явной политики клиента отклоняется при создании соединения: включение реплик не должно молча менять заявленные гарантии.

Параметры приложения для стенда с двумя кандидатами и требованием одной удалённой копии:

```dotenv
DURABILITY_REQUIRED_STANDBYS=1
DURABILITY_STANDBY_NAMES=gigaquizz_ha_a,gigaquizz_ha_b
```

Ожидаемое серверное значение — `synchronous_standby_names = 'ANY 1 (gigaquizz_ha_a,gigaquizz_ha_b)'`. Поддерживается только этот явный формат ANY с уникальными именами в заданном порядке, без `*`, кавычек и смены кандидатов во время работы Store. После смены состава, перезапуска primary или продвижения реплики нужно явно пересоздать Store с политикой нового владельца.

Для каждой положительной квитанции `accepted`, `duplicate`, `conflict` выполняется следующее:

1. Соединение с primary закрепляется за операцией. SQL-функция заканчивает неявную транзакцию; клиент полностью считывает её завершение.
2. Последующий запрос один раз захватывает `pg_current_wal_insert_lsn()`. Эта позиция WAL покрывает commit наблюдавшегося голоса, включая победившую конкурентную запись или прежний commit с потерянным подтверждением.
3. Проверяются локальный flush и `flush_lsn` требуемого числа разных разрешённых физических standby. Для standby обязательны `streaming`, `quorum` и активный physical replication slot. Повторная проверка использует ту же позицию WAL, а не передвигает цель при новой нагрузке.
4. На каждой проверке сверяются настройки сохранности, system identifier, timeline и время запуска postmaster. До успешного доказательства результат не передаётся вызывающему коду как подтверждённый.
5. Ошибка, отсутствие прав, нехватка реплик, изменение владельца/конфигурации или deadline возвращают ошибку сохранности. Vote API уже отображает такие неопределённые исходы как 503 с возможностью повторить тот же ID и выбор.

Проверка применяется также после создания опроса, миграции, подсчёта и чтения результатов. Реплицированный `Ping` проверяет достижимость нужной сохранности; это проверка на данный момент, не обещание доступности следующего запроса. `WaitDurable` доступен экспериментальному генератору для проверки завершённых контрольных записей на том же фиксированном primary.

Причина отдельной проверки: PostgreSQL может отменить ожидание SyncRep после локального commit с предупреждением. Read-only повтор сам по себе не ждёт прежнюю репликацию. Код не использует текст предупреждения как доказательство: язык и настройки сообщений могут меняться. Даже если SQL завершился без ошибки, положительный прикладной ответ проходит WAL-проверку. Если реплика успела восстановиться и нужная позиция надёжно записана, успешный ответ снова допустим. Основание: [PostgreSQL 16: SyncRep](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/replication/syncrep.c#L297-L310).

Корректность опирается на включённые `fsync` и `full_page_writes` на primary и надёжный flush физических standby. Стенд также включает их на репликах; драйвер не может доказать исправность удалённого накопителя по одному полю `flush_lsn`. `write_lsn` недостаточен, а `replay_lsn` для сохранности не требуется: после ACK данные могут ещё не быть доступны для чтения на standby. Позиции описаны в [PostgreSQL 16: pg_stat_replication](https://www.postgresql.org/docs/16/monitoring-stats.html#MONITORING-PG-STAT-REPLICATION-VIEW).

Это консервативный механизм для измерений на одном фиксированном владельце. Он не реализует обнаружение отказа, выбор нового лидера, защиту от двух одновременно работающих primary и распределённое владение ключами. При переключении старый владелец должен быть остановлен или надёжно лишён права записи внешним механизмом. Проверка `pg_is_in_recovery() = false` не заменяет такую защиту. Локальный стенд на одном компьютере не подтверждает независимость зон и не переживает потерю этого компьютера.

Проверка выполняется отдельным запросом после каждого положительного результата. При коротком отставании она повторяется с паузами 1, 2, 4, затем максимум 5 мс: это уменьшает ожидание исправной реплики, а при долгой недоступности частота возвращается к прежнему пределу. Начальная версия всегда ждала 5 мс; изменение проверяется в нагрузочных и отказных опытах. Target остаётся фиксированным, каждый повтор заново проверяет тот же набор условий. Ожидание ограничено исходным контекстом и дополнительным пределом 10 секунд. Глобальная позиция WAL может включать лишние конкурентные записи и увеличивать задержку. Объединение проверок нескольких операций в один подтверждённый префикс — возможная последующая оптимизация после измерений, с сохранением границы доказательства каждого commit.

`Store.Warm` открывает все настроенные соединения до приёма HTTP-трафика, проверяет их и требуемую сохранность; при ошибке запуска HTTP-listener не происходит. Это прогрев соединений, а не всех страниц данных или SQL-планов. Через защищённые административные метрики доступны накопительные времена SQL голосования, SQL-проверок WAL, фактического ожидания между проверками и получения соединения. Отдельно считаются повторные проверки и создания новых соединений. Метрики не содержат токены или тексты запросов; времена отдельных операций могут пересекаться, поэтому их нельзя складывать как время работы всего сервера.

Рабочему пользователю реплицированного режима нужны права чтения полных сведений репликации и выполнения `pg_control_system`; недостаточные права дают отказ. Текущий timeline определяется по имени WAL через `pg_walfile_name`, поскольку timeline последнего checkpoint может временно отставать после promotion. Локальный стенд использует собственную служебную роль в закрытом Unix socket. Для внешнего размещения нужен отдельно ограниченный интерфейс мониторинга либо обоснованные grants; выдача приложению полного superuser-доступа не является рекомендуемой производственной настройкой.

Изменений схемы голосов для этого этапа нет. Миграция 001 остаётся неизменной; прикладная атомарность, дедлайн и правило первого выбора сохраняются. Набор тестов должен отдельно подтвердить: конкурентные повторы, потерянный ACK, отмену SyncRep, запрет подтверждений до восстановления реплики, замедленный replay при работающем flush, изменение политики и сохранность после управляемого продвижения реплики.
